## 1. What is asked

The Port Admin manages the port profile, the navigation channel with its reference depth level, the channel's ordered waypoints, and the port settings that change without code (`backend/atlantech_backend_tasks.md:88`). Roadmap done-when: "all of these can be read and edited with validation" (`roadmap/roadmap-tasks.json:728-736`). The settings editor is typed: the value is cast by its `value_type` and checked against `min_value` / `max_value` (handoff; CT-18 §4).

**Done when** (each line is checkable by a test or a demo; shapes depend on Q1 to Q8):

- [ ] `GET /port-profile` and `PATCH /port-profile` (only the fields the Port Admin owns, Q3), with `version`, validation of coordinates, IANA timezone and GeoJSON boundary.
- [ ] Navigation channel read and edit (`name`, `depth`, `depth_datum`, `width`, `speed_limit_knots`, `is_active`), with `version`; the CHECK `chk_channel_dimensions` is enforced in validation first (422, not a database error). Create and deactivate if more than one channel is allowed (Q1).
- [ ] Waypoints read and edited as an ordered list for one channel (Q2): unique labels, order 1..n, valid coordinates, in one transaction under the channel's version token.
- [ ] `GET /port-settings` lists every key with `value`, `value_type`, `min`, `max`, `description`, `updated_by`, `version`; `PATCH /port-settings/{key}` changes only the value: cast by type (INT, DECIMAL, BOOL, STRING, JSON), refused outside `min` / `max`, `updated_by` set, audited (CT-18 §4).
- [ ] The three CT-18 §4 cross-field rules are enforced when their keys exist (Q5).
- [ ] Every write: group `port.api`, `ability:` (Q4), `version.token:` on PATCH/PUT, `VersionToken::lockAndAssert` in the transaction, `AuditService` in the same transaction, `Idempotency-Key` in OpenAPI; refusals audited. `RouteAbilityCoverageTest`, `RouteVersionCoverageTest` stay green.
- [ ] OpenAPI updated (minor bump from 1.11.1) and published to PortHub; Pint and the full suite pass.

**Out of scope:** terminals and berths (P2-F2, Marwan) · safety constraints and tide sets (P2-F5) · seeding the AI keys (P2-F9) · the licence guard 423 for these writes (P2-D5, still a pass-through hook) · creating or deleting setting keys (keys come only from the seeds, CT-18 §3).

## 3. Design

### Endpoints (proposed; final after Q1 to Q4)

| Method and path | Ability | Request | Success | Errors (code) |
| --- | --- | --- | --- | --- |
| `GET /port-profile` | Q4 | — | 200 profile + `version` | 401 · 403 · 503 (no row) |
| `PATCH /port-profile` | `port-setup.manage` | Port-Admin fields (Q3) + `version` | 200 | 401 · 403 · 409 `VERSION_CONFLICT` · 422 |
| `GET /navigation-channels` | Q4 | — | 200 list (with waypoints) | 401 · 403 |
| `POST /navigation-channels` (if Q1 = many) | `port-setup.manage` | channel fields | 201 | 401 · 403 · 422 |
| `PATCH /navigation-channels/{channel}` | `port-setup.manage` | fields + `version` | 200 | 401 · 403 · 404 · 409 · 422 |
| `PUT /navigation-channels/{channel}/waypoints` | `port-setup.manage` | ordered list + channel `version` | 200 channel with waypoints | 401 · 403 · 404 · 409 · 422 |
| `GET /port-settings` | `port-setup.manage` (Q4) | — | 200 list | 401 · 403 |
| `PATCH /port-settings/{setting_key}` | `port-setup.manage` | `value` + `version` | 200 | 401 · 403 · 404 · 409 · 422 |

### Data

- Tables (all Backend-owned, CT-15): `port_profiles`, `navigation_channels`, `channel_waypoints`, `port_settings`; audit rows in `audit_logs`. No migration. Workers only read them, so no `ai-impact` label.
- Rules enforced in code: latitude/longitude ranges; IANA timezone (`timezone:all`); boundary is a GeoJSON Polygon with `[lon, lat]` pairs; channel depth, width and speed > 0; waypoint labels unique per channel and order 1..n; setting value parsed by `value_type` (INT integer, DECIMAL number, BOOL `true`/`false`, STRING ≤ 255, JSON valid JSON ≤ 255 chars stored) and inside `min_value` / `max_value` when set.

### Behaviour

- Write chain (F11): `port.api` → `ability:port-setup.manage` → `version.token:<param>` on updates → controller opens a transaction → `VersionToken::lockAndAssert` → rules → save → `AuditService::recordUpdated` / `recordCreated` in the same transaction → resource with the new `version`.
- Waypoint list: replaced inside the channel's transaction; the channel's `updated_at` is touched so its `version` covers the waypoints (the waypoint table has no `updated_at`). Deleting old rows depends on Q2.
- Settings: `updated_by` = the actor; the audit row has before/after value. Workers read per job, so nothing else is notified.
- Licence mode: the 423 hook stays a pass-through until P2-D5; nothing to do here beyond being inside `port.api`.
- Events: none. A master-data change does not touch pending recommendations for these tables (FR-MD-06 is about berths).
