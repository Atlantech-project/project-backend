## 1. What is asked

The Port Admin (`PORT_GM`) manages terminals and berths (`roadmap/roadmap-tasks.json:740-748`, `backend/atlantech_backend_tasks.md:89`).
A terminal is created as Container Terminal (`CONTAINER`) or Non-Container Terminal (`NON_CONTAINER`), with code and name, and GeoJSON boundary coordinates (from table comment). Creating a terminal automatically creates an `organization_unit` of type `TERMINAL`.
Berths require code, length, water depth, depth datum, and maximum vessel LOA (`max_vessel_loa <= length`). Each berth must serve at least one terminal (`berth_terminals`), and shared berths (a berth assigned to multiple terminals) are permitted (DEC-51). Neither terminals nor berths are deleted; they are updated or deactivated (FR-MD-05).

**Done when** (each line is checkable by a test or a demo):

- [ ] `POST /terminals` creates a terminal (`code`, `name`, `terminal_type`, `boundary_coordinates`) and an `organization_unit` (`unit_type = TERMINAL`, `terminal_id`) in the same database transaction; `code` and `terminal_type` are immutable after creation (`name` stays editable).
- [ ] `GET /terminals` and `GET /terminals/{terminal}` return terminal details, active status, GeoJSON boundary, associated berths, and `version` (`VersionToken::of`); routes carry `terminal.scope` where `{terminal}` exists.
- [ ] `PUT /terminals/{terminal}` updates name and boundary coordinates under version lock (`version.token:terminal`), rejecting modifications to `code` or `terminal_type`.
- [ ] `POST /terminals/{terminal}/deactivate` sets `is_active = 0` under version lock; `POST /terminals/{terminal}/activate` reactivates it. Deactivating an inactive terminal (or activating an active one) is a no-op: 200 with the unchanged resource, no audit row (as `UserAdministrationService::deactivate`).
- [ ] `POST /berths` creates a berth and associates at least one active terminal in `berth_terminals` in the same transaction; `code` is immutable after creation.
- [ ] A berth with `max_vessel_loa > length` or non-positive dimensions is rejected with 422 `VALIDATION_FAILED` (`chk_berth_loa_fits`, `chk_berth_dimensions`).
- [ ] Validation enforces DB check limits: latitude between -90 and 90, longitude between -180 and 180, decimal ranges (`length` and `max_vessel_loa` <= 99999.99, `water_depth` <= 9999.99), and string lengths (`terminal.code` <= 20, `berth.code` <= 30, `terminal.name` <= 120, `berth.name` <= 80).
- [ ] A berth with no terminals (`terminal_ids` empty, missing, or invalid) is rejected with 422 `VALIDATION_FAILED`. Adding a **new** link to an inactive terminal is rejected with 422 (`errors.berths.terminal_inactive`); links that already exist stay valid on update even if their terminal was deactivated later.
- [ ] `depth_datum` must equal the `depth_datum` of every existing `navigation_channels` row, on create and on update (422 `errors.berths.datum_mismatch`); with no channel row the check is skipped. The tide set check belongs to P2-F5.
- [ ] Shared berths work: a berth can link to multiple terminals (`berth_terminals` contains multiple rows, DEC-51).
- [ ] `GET /berths` (filters: `status`, `terminal_id`, `q`) and `GET /berths/{berth}` return berth details, assigned terminals, and `version`; `GET /berths?terminal_id=` validates scope via `TerminalScope::authorize`.
- [ ] Terminal-scoped roles (`TERMINAL_ADMIN`, `TERMINAL_OFFICER`) see only their terminal and its berths: `GET /terminals` uses `TerminalScope::restrict` on `id`, `GET /berths` restricts through `whereHas('berthTerminals')` on `terminal_id` (a shared berth shows for every linked terminal), and `GET /berths/{berth}` refuses a berth not linked to the user's terminal with 403 through `AccessRefusal` (the route has no `{terminal}`, so `terminal.scope` does not cover it). Port-wide roles see everything.
- [ ] `PUT /berths/{berth}` updates berth attributes and syncs `terminal_ids` under version lock (`version.token:berth`), ensuring at least one terminal remains.
- [ ] Attempting to detach a terminal from a berth when the `(berth_id, terminal_id)` pair is referenced in `safety_constraints` or `recommendation_options` is refused with 409 `CONFLICT` and audited as `REJECTED_ATTEMPT`.
- [ ] Any change to `terminal_ids` writes an explicit audit entry with before/after `terminal_ids`, whether or not other berth fields changed. When only `terminal_ids` changed, `$berth->touch()` advances `updated_at` so the version token moves.
- [ ] `POST /berths/{berth}/deactivate`, `activate`, and `maintenance` update berth `status` (`ACTIVE`, `MAINTENANCE`, `INACTIVE`) under version lock.
- [ ] Every berth mutation (create, update, deactivate, activate, maintenance) dispatches domain event `ResourceChanged` after commit (class from Mariam's Day 1 PR).
- [ ] Refused business rule attempts (409 `CONFLICT` on terminal detachment) are audited as `REJECTED_ATTEMPT` via `AuditService::rejectedAttempt`. A 409 `VERSION_CONFLICT` is **not** audited by the services: `EnsureRecordVersion` already records it. 422 validation failures are not audited.
- [ ] Routes sit in group `port.api`; writes require `ability:port-setup.manage`; reads require `ability:port-state.read`.
- [ ] OpenAPI spec (`openapi/port-api.yaml`) includes `IdempotencyKey` and 422 response on all write endpoints.
- [ ] Architectural guard tests (`RouteAbilityCoverageTest`, `RouteVersionCoverageTest`, `WriteChainOrderTest`, `OpenApiDriftTest`, `ModuleArchitectureTest`) pass.

**Out of scope:**
- Licence guard limit checks (`max_terminals`, `max_berths`): DEC-54 marks licence enforcement as future work.
- Terminal productivity profiles (P2-F6).
- Yard zones, blocks, and slots (P2-F4).
- Point-in-polygon verification for terminal boundary against port boundary (known gap; also listed in BE-PK3).
- Ending or moving role assignments of users in a deactivated terminal's unit: the Port Admin does it by hand with P2-E2 (Q8).
- Berthing requests on a deactivated terminal: handled per status in P3-G1/P3-G3 and later (Q8). A request past preliminary approval is not moved to another terminal: the approval was given for that terminal, so a new terminal needs a new approval. Cancel and re-create is the intended path (lead, 2026-11-24); SM-4 is not changed.

### Data, Validation, and Transactions

1. **Immutable Fields:**
   * `terminals.code`, `terminals.terminal_type`, `berths.code` are read-only on updates: the update requests mark them `prohibited`, so sending them answers 422 (clearer for the frontend than silently ignoring them). `terminal_type` is part of the composite FKs from `storage_facilities`, `terminal_productivity_profiles` and `terminal_recommendations`; the two codes are business identifiers.
2. **Terminal Creation (`TerminalService::create`):**
   Runs inside `AuditService::transaction()`:
   * Creates `terminals` record.
   * Creates `organization_units` record (`unit_type = UnitType::Terminal`, `terminal_id = $terminal->id`).
   * Calls `$audit->recordCreated($terminal, $actorId)`.
3. **Berth Creation (`BerthService::create`):**
   Runs inside `AuditService::transaction()`:
   * Asserts `max_vessel_loa <= length` and positive dimensions.
   * Asserts `terminal_ids` has at least 1 existing active terminal ID.
   * Asserts `depth_datum` equals the `depth_datum` of every `navigation_channels` row (skipped when there is none).
   * Creates `berths` record.
   * Attaches `$terminalIds` in `berth_terminals`.
   * Calls `$audit->recordCreated($berth, $actorId)`.
   * Dispatches `ResourceChanged` after commit.
4. **Berth Update and Safe Terminal Sync (`BerthService::update`):**
   Runs inside `AuditService::transaction()`:
   * Locks berth under `VersionToken::lockAndAssert($berth, $version)`.
   * The service takes `string $route` from the controller (method and path, as `UserController::route()` in P2-E1); it never reads the `Request`.
   * Asserts the `depth_datum` rule (same as create) when `depth_datum` is sent.
   * Computes `$added` and `$removed` from the current and the new `terminal_ids`. Every id in `$added` must be an active terminal (422 `errors.berths.terminal_inactive`); ids already linked are not re-checked.
   * If any `(berth_id, terminal_id)` in `$removed` exists in `safety_constraints` or `recommendation_options`:
     * Calls `$audit->rejectedAttempt($route, ErrorCode::Conflict, 'terminal_in_use', $actor->id, $actor->username, 'berths', $berth->id)`.
     * Throws 409 `ApiProblemException::conflict('berths.terminal_in_use')`.
   * Saves the berth attributes; if the save changed anything: `$audit->recordUpdated($berth, $actorId)`.
   * Syncs `berth_terminals` with the new list (retaining >= 1 terminal). If `$added` or `$removed` is not empty:
     * Always audits the pivot change via `$audit->record(AuditLogAction::Update, 'berths', $berth->id, $actorId, ['terminal_ids' => $oldIds], ['terminal_ids' => $newIds])`, whether or not attributes changed too.
     * If the save changed nothing, calls `$berth->touch()` so `updated_at` (the version token) moves.
   * Dispatches `ResourceChanged` after commit.
5. **Berth status changes (`BerthService::deactivate` / `activate` / `maintenance`):**
   * Same transaction, lock and `recordUpdated` pattern; a call that would set the current status is a no-op (200, no audit row, no event).
   * Dispatches `ResourceChanged` after commit when the status changed.
6. **Terminal deactivation (`TerminalService::deactivate` / `activate`):** sets `is_active`; no-op when already in that state (Q8):
   * Berths are not changed. A berth whose only terminal is inactive keeps its `status`; readers skip berths with no active terminal and skip `(berth, terminal)` pairs whose terminal is inactive (shared berths).
   * Dispatches `ResourceChanged` after commit for every berth linked to the terminal, so pending recommendations that use them are regenerated (FR-MD-06, P4-K5).
   * Roles in the terminal's unit stay active; nothing is ended. Open berthing requests are not touched.
7. **Inactive terminal is read-only for terminal-scoped roles (Q8):** a non-GET request by a terminal-scoped user on an inactive terminal is refused with 409 `CONFLICT` (`errors.terminals.terminal_inactive`) and audited through `AccessRefusal`. Implemented once in `TerminalScope` (used by `terminal.scope` for `{terminal}` and by `TerminalScope::authorize` for body/query ids), so P2-F4 and P2-F6 get it for free. Reads stay allowed. Port-wide roles (Port Admin) are not affected.
8. **Message keys** (`lang/en/errors.php`, plural areas like `users`): `berths.terminal_in_use`, `berths.terminal_inactive`, `berths.datum_mismatch`, `terminals.terminal_inactive`.
