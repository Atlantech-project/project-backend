## 1. What is asked

Turn the agreed Port database design into Laravel migrations, so `php artisan migrate:fresh` on an empty MySQL 8.4 database creates every table of the design. The design is the one set by CT-17 v1.0 (approved 2026-10-27), with the latest contract and decision updates synced into `docs/reference/` on 2026-10-28 (commit `c1af9ce`: CT-08, CT-17 and CT-18 approved, DEC-35 and DEC-36 closed, `contracts/db/table-names.md`).

**Done when** (each line is checkable by a test or a demo):

- [ ] `php artisan migrate:fresh` runs clean on an empty MySQL 8.4 database (Docker `mysql` service).
- [ ] The database holds the 92 port tables with the plural names in `contracts/db/table-names.md`, plus the Laravel framework tables (`cache`, `cache_locks`, `jobs`, `job_batches`, `failed_jobs`, `sessions`, `password_reset_tokens`, `migrations`).
- [ ] Every id and foreign key is `BIGINT UNSIGNED`; foreign-key, constraint and index names are the ones in `PortSync.sql` / `PortSync_base_ddl_fixes.sql`; engine InnoDB, `utf8mb4` / `utf8mb4_0900_ai_ci`.
- [ ] Every CHECK constraint and generated column from the base DDL fixes and Report A exists and is enforced (a test inserts a breaking row and gets a constraint error).
- [ ] The CT-17 §7 first-batch additions exist: `yard_runs`, `baplie_parse_runs`, `result_handled_at` (4 run tables), `notified_at` (`drift_measurements`), `rationale_params` (2 tables).
- [ ] The FCM changes exist: `user_devices.push_token`, `push_token_updated_at`, its unique index and check; `PUSH` in `notification_logs.channel` with its check.
- [ ] DEC-36: `uq_ura_active` is unique on (`user_id`, `active_assignment_key`); a second active role for the same user is refused.
- [ ] DEC-35: `users` has `username` (unique, lowercase check) and no email column.
- [ ] `updated_at DATETIME(6)` on the master-data tables listed in section 3.
- [ ] The DB connection runs in UTC (`time_zone = '+00:00'`).
- [ ] `database/grants/workers.sql` creates the six worker accounts with the DEC-08 grant matrix and runs clean after the migrations.
- [ ] `composer contracts:schema` writes `contracts/db/schema.sql` (mysqldump, no data, header with last migration and contract version).
- [ ] `php artisan test` passes (existing 20 tests plus the new schema tests).

**Out of scope:** reviewing each table against the class diagrams (P1-B2, P1-B3) · Eloquent models and PHP enums (P1-B5) · seeders and `port_settings` rows (P1-B6, CT-18) · Central SaaS database (P1-B7, DEC-56) · Sanctum and `personal_access_tokens` with `revoked_at` (P1-C1 / P1-C3) · the PortHub PR that publishes `schema.sql` and moves the submodule pointer (after this PR merges).

## 3. Design

### Endpoints

None.

### Data

- **Input:** `docs/reference/database/PortSync.sql` + base DDL fixes + Report A final forms + FCM changes 1 and 3 + CT-17 §7 additions + DEC-36 index.
- **Migrations:** one per table, `…_create_<table>_table.php`, ordered by module so every foreign key points to an earlier table. Columns, types, defaults, comments (UTF-8 fixed), ENUMs with the exact SQL names, indexes and FK names as in the SQL. Ids `id()` / `foreignId()` (BIGINT UNSIGNED). No `ON DELETE CASCADE` on tables a worker writes.
- **CHECKs and generated columns:** created inside each table's migration (`DB::statement` after `Schema::create`), named as in the DDL fixes (answer 1).
- **`updated_at DATETIME(6)`** (answer 3) on: `users`, `terminals`, `berths`, `tugboats`, `safety_constraints`, `port_shifts`, `equipment`, `storage_facilities`. Tables already carrying `updated_at` keep it, changed to `DATETIME(6)`. Other master-data tables edited from the screens are added during the P1-B2 review.
- **Framework tables:** keep `cache` and `jobs` migrations; the default `users` migration is replaced by the port `users` table, keeping `password_reset_tokens` and `sessions`.
- **Connection:** `config/database.php` sets `timezone => '+00:00'` and the collation `utf8mb4_0900_ai_ci`.
- **Grants:** `database/grants/workers.sql`, the DEC-08 matrix plus the CT-17 §7 column grants.
- **Owner:** Backend for every migration (CT-17). Tables workers read or write are listed in CT-15; this first batch is reviewed by the AI Team as part of CT-17 itself, so no `ai-impact` approval is needed beyond the CT-17 sign-off.
- **Enums:** stay as MySQL `ENUM`; PHP enums come in P1-B5.

### Behaviour

Not applicable (no endpoint, no write chain, no audit, no events).

### How the migrations are produced (answer 2)

A one-off Node script, kept outside the repository, reads the corrected SQL, sorts the tables by foreign key, maps names with `table-names.md`, and writes one Schema-builder migration per table. The output is then reviewed and fixed by hand; from this PR on, the migrations are the source of truth (CT-17 §1) and the script is not used again.
