## 1. What is asked

Announce a `ResourceChanged` event after the commit whenever a tug, a pilot or CT equipment changes, so that P4-K5 can later regenerate the pending recommendations that use it. Berth changes are already announced (P2-F2). Roadmap done-when: "a resource change reliably triggers the event".

**Done when:**

- [x] Every change in the table of section 3 dispatches exactly one `ResourceChanged` per affected resource, with the right kind and id.
- [x] Nothing is dispatched for a refused request (403, 409, 422), a rolled-back transaction or a request that changes nothing.
- [x] Listeners run only after the commit.
- [x] `ModuleArchitectureTest` passes.

**Out of scope:** the listener, the C-02 job and the READ_ONLY rule of FR-RC-16 (P4-K5, P3-I1) · berth and terminal dispatches (done in P2-F2) · resources released by a plan cancellation (P4-L2) · yard changes (not one of the four resource kinds) · any API, schema or contract change.

## 3. Design

Dispatch inside the write transaction (the event itself waits for the commit), only when something was actually saved, and once per resource per request.

| Change (service) | Event | Source |
| --- | --- | --- |
| Tug updated with a change that affects planning (`TugboatService::update`: status, power, capacity). A new tug sends nothing (Q2) | `TUG` tug id | Q1 |
| Pilot rank changed, activated or deactivated (`PilotService`). A new pilot sends nothing (Q2) | `PILOT` user id | Q1 |
| Pilot name or phone only (`PilotService::update`) | none | Q1 |
| Pilot schedule entries added or removed (`ShiftScheduleService`) | `PILOT`, once per pilot | (none) |
| Tug master schedule entries added or removed (`ShiftScheduleService`) | `TUG` of the assigned tug, once per tug; none if unassigned | CT-10 |
| Existing tug master linked, moved or unlinked (`TugMasterService::assignTugboat`). A new tug master sends nothing, even with a tug (Q2) | `TUG` for the old and the new tug | Q3 |
| Tug master activated or deactivated (`TugMasterService`) | `TUG` of the linked tug (the one held before the link is cleared) | Q3 |
| Tug master name or phone only | none | Q1 |
| `/users` deactivate, role end or role replacement of a pilot or tug master (`RoleEndHandler` implementation) | `PILOT` user id; for a tug master `TUG` of the tug that was linked | Q4 |
| `/users` activate, or assigning the role again, for a pilot | `PILOT` user id (new `Access` hook); a tug master sends nothing (returns without a tug) | Q4 |
| Equipment created, or updated with a change of quantities or capabilities (`EquipmentService`) | `EQUIPMENT` equipment id | Q2 |
| Port shift edit | none: P2-F3 refuses to change the times of, or deactivate, a shift that is scheduled from today | (none) |
| Pilot rank limit value changed (`PilotRankLimitService::update`); no change or a refused edit sends nothing | `PILOT` user id, once for each active pilot of that rank | Q5 |

- **Data, API, contracts:** no endpoint, response, migration, enum or OpenAPI change. No audit change: the events carry no data of their own.
- **Modules:** every dispatch is in `MasterData`. The `/users` cases go through the `RoleEndHandler` implementation (today `TugLinkRoleEndHandler`), so `Access` still imports nothing from `MasterData`.
- **Locks and transactions:** one new lock: `UserAdministrationService::activate` locks the active role assignment after the user row and after the plan-limit count (same order as `deactivate`). The handlers read profiles without locks.
