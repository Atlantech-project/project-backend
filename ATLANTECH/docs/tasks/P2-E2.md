## 1. What is asked

The Port Admin gives a user a role, checked against the organization unit, and ends it by setting `active_to`; the role history stays visible (`roadmap/roadmap-tasks.json:691-699`, `backend/atlantech_backend_tasks.md:81`). DEC-36 (Closed 2026-10-28, `decisions/ATLANTECH_Decisions.md:1019-1042`): a user has one active role; assigning a new one ends the current one and inserts the new row in the same transaction; rows are never deleted.

**Done when:**

- [ ] `POST /users/{user}/roles` with `role` (and `terminal_id` for the three `TERMINAL_*` roles) ends the user's active role and inserts the new one in one transaction; `GET /users/{user}` shows the new active role and the old one in `role_history` with `active_to` set.
- [ ] A terminal-scoped role without `terminal_id`, or any other role with a `terminal_id`, or a `terminal_id` with no organization unit → 422 `VALIDATION_FAILED` (FR-AC-11). A role that does not fit the unit type can never be written (`chk_ura_role_matches_unit` is the backstop; the service derives the unit from the role).
- [ ] `POST /users/{user}/roles/end` sets `active_to` on the active role; the user is left without a role (every request then answers 403 `no_active_role`, existing D1 behaviour).
- [ ] Ending or replacing the last active `PORT_GM` role → 409 `CONFLICT` (`errors.users.last_port_admin`), also under parallel attempts, audited as `REJECTED_ATTEMPT` (FR-AC-12).
- [ ] The Port Admin may change or end their own role and may assign a role to a deactivated user (lead's answers), as long as the last-admin rule holds.
- [ ] Assigning the role and unit the user already holds is a no-op: 200, same `version`, no new history row, no audit row.
- [ ] A role change moves the user's `version` (the `users.updated_at` token is touched), so a stale `version` → 409 `VERSION_CONFLICT`; two parallel changes: one commits, the other gets 409.
- [ ] Every change is audited in the same transaction; OpenAPI and readiness pack updated.

**Out of scope:** creating users (E1); the role/ability matrix (D1: a new role value needs a new `Ability` row there, not here); creating organization units for terminals (P2-F2 creates the TERMINAL unit with each terminal); changing `name` or `phone`; role changes in bulk.

## 3. Design

### Endpoints

Group `port.api`, `ability:users.manage`, `version.token:user` on both (the user's token), `{user}` bound after the ability check.

| Method and path | Request | Success | Errors (code) |
| --- | --- | --- | --- |
| `POST /users/{user}/roles` | `role` (one of the 12), `terminal_id` (required for `TERMINAL_ADMIN`, `TERMINAL_OFFICER`, `TERMINAL_SUPERVISOR`; forbidden otherwise), `version` | 200 `UserDetailResource` (active role, `role_history`, new `version`) | 401, 403, 404, 409 `VERSION_CONFLICT`, 409 `CONFLICT` (last Port Admin), 422 `VALIDATION_FAILED` |
| `POST /users/{user}/roles/end` | `version` | 200 `UserDetailResource` (no active role) | 401, 403, 404, 409 `VERSION_CONFLICT`, 409 `CONFLICT` (last Port Admin), 422 |

Ending when the user has no active role is a no-op: 200, same `version`.

### Data

- Written: `user_role_assignments` (update `active_to`, insert), `users.updated_at` (touch, the version token), `audit_logs`. Read: `organization_units`, `users`. Owner: Backend (CT-15). No migration; `schema.sql` unchanged.
- Unit rule in code: `HARBOUR_AUTHORITY` roles (`PORT_GM`, `PORT_STAFF`, `MARINE_SAFETY_OFFICER`) → the one HARBOUR_AUTHORITY unit; `MARINE_SERVICES` roles → the one MARINE_SERVICES unit; `TERMINAL_*` roles → the TERMINAL unit whose `terminal_id` is the request's. Access reads `organization_units.terminal_id` instead of `terminals`, so Access does not import MasterData. If the HARBOUR_AUTHORITY or MARINE_SERVICES unit does not exist yet, the service creates it with `firstOrCreate` (they are singletons; production has none until a seeder or provisioning makes them; E1's first-admin seeder creates the first one). An unknown `terminal_id` (no unit) → 422 `errors.terminal_id`.
- `active_to` value: `boundary = max(now, old.active_from + 1 second)`. The ended row gets `active_to = boundary` and the new row `active_from = boundary`, so there is no gap and `chk_ura_period` (`active_to > active_from`, seconds precision) holds even if a role is replaced within the second it was given.

### Behaviour

- **Order (P2-D2):** auth · password gate · `ability:users.manage` · binding · `version.token:user` (early check) · FormRequest validation · business rules (last Port Admin). No plan limit (a role does not add a user).
- **Transaction (`AuditService::transaction`):** (1) lock the admin set plus the target `users` rows `FOR UPDATE` in id order, the same helper E1's deactivate uses; (2) `VersionToken::lockAndAssert` on the target; (3) read the active assignment `FOR UPDATE`; (4) same role and unit as requested → no-op; (5) last-admin rule: the current active role is `PORT_GM` and the change removes it (end, or a different role/unit) and no other locked user is `is_active` with an active `PORT_GM` assignment → refuse; (6) update the old row, insert the new row, `touch()` the user, audit.
- **Rule counts "active admins" the same way as E1:** a user counts if `users.is_active = 1` and holds an active `PORT_GM` assignment.
- **Audit (same transaction):** UPDATE `user_role_assignments` for the ended row (`active_to` null → value), CREATE for the new row (`recordCreated`), both with the Port Admin as actor; no row for the `touch`. Refusals: `AuditService::rejectedAttempt(route, ErrorCode::Conflict, 'last_port_admin', actorId, username, 'users', targetId)` after the rollback.
- **Effect on the target:** the next request of that user reads the new role (the scope is memoised per request only). The user's open sessions stay valid; they get the new abilities immediately.
- **Licence mode:** a normal write, so blocked in READ_ONLY once P2-D5 fills the hook (only deactivation and device revocation are allowed there).
- **Events and messages:** none.
