## 1. What is asked

Every change request passes the same checks in the same order, and each check answers with its own code (`roadmap/roadmap-tasks.json:642-650`, `backend/atlantech_backend_tasks.md:70`). The order is FR-GL-01 (`requirements/Functional Requirements.md:83`) and CT-01 §7 (`contracts/api-conventions.md`, last paragraph before §8):

1. authentication · 401 `UNAUTHENTICATED`
2. password gate · 403 `PASSWORD_CHANGE_REQUIRED` / `ACCOUNT_DISABLED`
3. role (`ability`) then terminal scope (`terminal.scope`) · 403 `FORBIDDEN`
4. minimum app version, mobile · 426 `APP_UPDATE_REQUIRED`
5. licence mode and port status · 423 `LICENSE_READ_ONLY`
6. record version token · 409 `VERSION_CONFLICT`
7. business rules · 409 or 422
8. plan limits · 422 `PLAN_LIMIT_EXCEEDED`

D2 builds the **order** and the **named places** for the steps; it does not build the contents of steps 4, 5, 6 and 8 (decision of the lead, answered in section 8: "hooks only, I wait for the rest").

**Done when** (each line is checkable by a test or a demo):

- [ ] One named middleware group `port.api` holds `auth:web` and the password gate (`EnsureAccountUsable`) plus the two parameterless hooks (`EnsureMinAppVersion`, `EnsureLicenseAllowsWrite`). Routes add `ability:<name>`, `terminal.scope` and (D4) `version.token` themselves.
- [ ] The order is pinned by the middleware priority list in `bootstrap/app.php`: whatever order a route lists its middleware in, they run in the FR-GL-01 order. `SubstituteBindings` runs **after** `ability` and `terminal.scope` (lead's answer Q4), so an unauthorised caller gets 403 before any 404.
- [ ] The three hook points exist as classes with their final names and aliases (`app.version`, `license.write`, `version.token`); until the owning tasks fill them they pass the request through. Their positions in the order are tested.
- [ ] `routes/api.php`: the signed-in `auth/*` routes use `port.api`; behaviour unchanged (existing tests green).
- [ ] An order test proves each refusal beats every later one (401 before password gate before role before terminal before 426 before 423 before 409), by replacing the hook steps with refusing fakes in the test.
- [ ] A reverse-order test: a route that lists `terminal.scope`, `ability` and the hooks in the wrong order still runs them in the right order.
- [ ] Steps 7 and 8 (business rules, plan limits) are documented as "inside the endpoint, in this order" in the class doc of the group and in this plan; they are not middleware.
- [ ] Pint clean; `ModuleArchitectureTest` and `OpenApiDriftTest` green; full Pest suite green.

**Out of scope:**

- The 426 comparison (`X-App-Version` against `min_app_version`): **Menna's P1-C3** (lead's decision, 2026-11-03). D2 only creates the named hook `EnsureMinAppVersion`; it must not be duplicated.
- The licence guard (reads `license_states`, 423, route tags for READ_ONLY and SETUP allow-lists) and the plan-limit service (422): **P2-D5**. DEC-54 (Closed) marks licence work as future work; the classes stay pass-through.
- The version token itself (read `version`, compare with `updated_at`, 409 with `current`): **P2-D4**.
- Role and terminal checks (`ability`, `terminal.scope`, `AccessRefusal`): **P2-D1**. D2 orders them and never changes them.
- Replacing `AccessRefusal`'s audit call: P2-D3.

## 3. Design

### Names other tasks use

| Name | Where | Used by |
| --- | --- | --- |
| Middleware group **`port.api`** = `auth:web`, `EnsureAccountUsable`, `EnsureMinAppVersion`, `EnsureLicenseAllowsWrite` | defined in `bootstrap/app.php` (`$middleware->group`) | every signed-in route (P2-E1, P2-F1..F5, …) |
| Priority list (the order of FR-GL-01) | `bootstrap/app.php` (`$middleware->priority`) | all routes; the only place the order lives |
| Alias `app.version` → `EnsureMinAppVersion` (hook, pass-through) | `app/Modules/Access/Http/Middleware/EnsureMinAppVersion.php`; alias in `AccessServiceProvider` | P1-C3 (Menna) fills the body: reads `X-App-Version`, compares, throws `ApiProblemException::appUpdateRequired` |
| Alias `license.write` → `EnsureLicenseAllowsWrite` (hook, pass-through, acts on writes only) | `app/Modules/License/Http/Middleware/EnsureLicenseAllowsWrite.php`; alias in `LicenseServiceProvider` | P2-D5 fills the body (423) |
| Alias `version.token` → `EnsureRecordVersion` (hook, pass-through) | `app/Modules/Shared/Http/Middleware/EnsureRecordVersion.php`; alias in `SharedServiceProvider` | P2-D4 fills the body (409 with `current`) |
| Existing, not changed: `ability`, `terminal.scope` (D1), `EnsureAccountUsable` | Access | ordered by the priority list |

Business rules and plan limits (steps 7, 8) are code inside the controller or service, in that order: rules first, plan limits last. They are not middleware, because they need the validated record and the transaction. P2-D5's plan-limit service is called after the rules; P2-E1 is the first endpoint that does so (create user, plan limit).

### The order and how it is pinned

Laravel sorts a route's middleware by `$middleware->priority([...])` (by class, ignoring parameters such as `ability:users.manage`), so a route can list them in any order. D2 sets the list to, in this order:

`Authenticate` (`auth:web`) → `EnsureAccountUsable` → `EnsureAbility` → `EnsureTerminalScope` → `EnsureMinAppVersion` → `EnsureLicenseAllowsWrite` → `SubstituteBindings` → `EnsureRecordVersion`

(then the framework defaults that matter, e.g. throttling stays where it is today, in front of nothing that is listed.) The class list replaces the default priority list in `bootstrap/app.php`; the default entries that are not named above (session, `AuthenticateSession`, `Authorize`) are kept in their default relative order at the start.

**Open point verified in step 1, not decided here:** `EnsureTerminalScope` does not exist yet (D1 step 4). The list names it by `::class`; naming a class that does not exist yet is harmless. `terminal.scope` must read the raw route id because it now runs before `SubstituteBindings` (Q4); D1 step 4 builds it that way. Because Marwan owns both tasks, this is a note for D1 step 4, not a change to D1's files from this session.

Request kinds (lead's answer Q2): 401, password gate, `ability`, `terminal.scope` apply to every request; `EnsureMinAppVersion` to any request that carries `X-App-Version`; `EnsureLicenseAllowsWrite` and `EnsureRecordVersion` to writes only (POST, PUT, PATCH, DELETE).

### Behaviour

- Write chain steps that apply: all eight, in the order above (this task owns the order).
- Transaction and locks: none for the middleware. Steps 6-8 run inside the endpoint's transaction (FR-GL-02, FR-GL-06); the version compare of D4 happens under the row lock in the same transaction (decided in D4's plan).
- Audit: unchanged. Role and terminal refusals are audited by D1 through `AccessRefusal`; the password gate audits itself. The new hooks audit nothing until their tasks fill them (P2-D3 provides the audit service; refused 426/423/409 are then audited through it, FR-GL-02).
- Licence mode: the middleware order places the 423 step; whether a given route is allowed in READ_ONLY or SETUP is P2-D5.
- Events and messages: none.
- Channel: `port.api` uses `auth:web`. Menna's mobile token guard (P1-C3) needs the same chain with a different guard; she registers a sibling group (e.g. `port.api.mobile` = token guard + the same four members) and the priority list already orders all of them. D2 does not create it.
