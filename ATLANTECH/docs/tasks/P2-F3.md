## 1. What is asked

"Manage tugs, tug masters (one per tug), pilots, their ranks and the vessel sizes each rank may handle, port shifts, and pilot and tug master schedules. Done when every resource the AI needs can be maintained." (`roadmap/roadmap-tasks.json:765-773`; task row `backend/atlantech_backend_tasks.md:90`.) The lead's Sprint 3 hand-off adds: any overlap is refused.

**Done when** (each line is a test or a demo):

- [ ] Tugs: the Tug Manager creates, reads, updates a tug (name, power, power unit, capacity) and sets its status to `AVAILABLE`, `MAINTENANCE` or `INACTIVE` (deactivate = `INACTIVE`, row kept). FR-MD-07.
- [ ] Tug masters: the Tug Manager creates a tug master in one call (user + `TUG_MASTER` role in `MARINE_SERVICES` + `tug_master_profiles` row, active-user plan limit checked, one-time password returned), reads, updates, links or unlinks a tug, and deactivates; deactivation clears the tug link in the same transaction. FR-MD-08.
- [ ] A second tug master for the same tug is refused (422, per FR-MD-08; see Q6), also under a race (lock + the `UNIQUE` index).
- [ ] Pilots: the Pilotage Manager creates a pilot in one call (user + `MARINE_PILOT` role + `pilot_profiles` row with rank, plan limit checked), reads, updates, promotes (changes rank) and deactivates. FR-MD-09.
- [ ] Rank limits: the three `pilot_rank_limits` rows can be read and their `max_vessel_loa` updated (NULL = no limit; > 0 otherwise). FR-MD-09, AI-051.
- [ ] Port shifts: create, read, update, activate and deactivate; an active shift whose time of day overlaps another active shift is refused, back-to-back shifts and shifts crossing midnight are accepted (`PeriodOverlap::timesOfDay`), also under a race. AIBD-016.
- [ ] Pilot schedules and tug master schedules: put a person on a shift for a date, list by date range and person, remove an entry; refused when the person is not an active pilot / tug master, the shift is inactive, or the entry already exists.
- [ ] Every write passes the write chain (ability 403, licence 423 hook, version token 409 where the row has `updated_at`), writes its audit row in the same transaction and refusals are audited as `REJECTED_ATTEMPT` where P2-D3 does so.
- [ ] OpenAPI describes every new endpoint (minor bump), the drift test and Spectral pass; CT-21 vocabulary unchanged (no new stored enum).

**Out of scope:** dispatching `ResourceChanged` (P2-F7; this task leaves a clear call site in each service) · the availability rule of DEC-32 and `RESOURCE_UNAVAILABLE` (P4-L1, P5-M1) · tug `BUSY` from the tablet (Execution, Phase 5) · turning `shift_date` + shift times into UTC instants (see Q12) · the screens (FE-066/068/069/078) · the licence allow-lists for READ_ONLY / SETUP (P2-D5).

## 3. Design

All code in `app/Modules/MasterData/` (models are there). Routes in `routes/api.php` under `port.api`. Writes use `AuditService::transaction`. Proposed names; final after section 8.

Schedule rows have no `updated_at`, so no version token; the unique key `uq_*_schedule` is the race guard.

Person routes (Q5): `{user}` on `/pilots/…` binds only a user with a `pilot_profiles` row, on `/tug-masters/…` only one with a `tug_master_profiles` row; any other user answers 404, so a manager can never deactivate or edit someone outside their department. Create fixes the role (`MARINE_PILOT` / `TUG_MASTER` in `MARINE_SERVICES`); the request carries no role. "Tug already has a master" answers 422 `VALIDATION_FAILED` with `errors.tugboat_id` (Q6). Person and schedule reads include the person's `is_active` (Q4).

### Data

- Tables (all Laravel-written, workers read, CT-15): `tugboats`, `tug_master_profiles`, `tug_master_schedules`, `pilot_profiles`, `pilot_rank_limits`, `pilot_schedules`, `port_shifts`; plus `users` and `user_role_assignments` through the Access services.
- Migrations: none. Seeder: add the three `pilot_rank_limits` rows (NULL = no limit) to the reference seed, since nothing seeds them today (Coding notes :111).
- Enums (CT-21): reuse `PilotRank`, `TugboatStatus`, `TugPowerUnit`; no new stored enum. Any helper enum carries `@not-stored`.
- Code rules (not in the database):
  - D-29: a pilot profile only for a user with active `MARINE_PILOT` in `MARINE_SERVICES`; same for `TUG_MASTER`.
  - One tug master per tug: checked with `lockForUpdate` on the tug's current profile row, the unique index as last guard (a duplicate-key error is turned into the same 422, never a 500).
  - Active port shifts never overlap: inside the transaction lock all active shifts (`lockForUpdate`), compare with `PeriodOverlap::timesOfDay`, excluding the shift itself on update.
  - Shift in use (Q8): a change of `start_time` / `end_time`, or `is_active` true → false, is refused with 409 `CONFLICT` `errors.port_shifts.in_use` when a `pilot_schedules` or `tug_master_schedules` row with `shift_date` ≥ today (port time zone) points at it. Checked under the shift's row lock; schedule inserts lock the shift row (`FOR SHARE`) so the two cannot race.
  - Deactivate a person (Q4): reuse the user deactivation (tokens revoked, `users.is_active = false`), keep the profile and the schedule rows; for a tug master also set `assigned_tugboat_id = NULL`, same transaction, with its own audit row.
  - Schedule entry: person active with the right role, shift active, `shift_date` not before today in port time (Q7).
  - Rank limits: `max_vessel_loa` null or > 0; after the change FIRST ≥ SECOND ≥ THIRD must hold, NULL counting as the largest; the three rows are locked together for the check (Q9).
  - Tug power unit: only `BOLLARD_PULL_TONNES` accepted on create / update (Q11; DEC-20 item 11). A stored HP / KW value is still shown on reads.
  - Tug status (Q10): the manager sets AVAILABLE, MAINTENANCE or INACTIVE; `BUSY` is refused (422 `errors.status`). The tug master link is kept on any status change.
  - Relink a tug master (Q10): lock the master's profile and the target tug's current profile; target taken → 422 `errors.tugboat_id`; the old tug is freed in the same write.
  - Schedule dates (Q7): `shift_date` before today in the port time zone → 422 `errors.entries.N.shift_date`; the list range is limited (proposed 62 days).

### Behaviour

- Write chain (P2-D2): `port.api` group + `ability:<name>` + `version.token:<param>` on rows with `updated_at`. No terminal scope (marine resources are port-wide).
- Transactions and locks: one `AuditService::transaction` per write; locks as listed above. Pilot / tug-master creation reuses the user-creation and role-assignment logic inside the same transaction (no nested service transactions that commit separately).
- Audit: CREATE / UPDATE rows per changed table (user, role assignment, profile, tug link); refused deactivations follow the P2-E1 pattern.
- Licence: all writes go through `license.write` (hook until P2-D5); reads always pass. Master data is set-up work, so it should be allowed in SETUP (P2-D5 decides; noted for that task).
- Events: none in this task. Each service marks where P2-F7 dispatches `ResourceChanged` (tug status, tug-master deactivate / relink / schedule change as `TUG`, pilot change as `PILOT`).
