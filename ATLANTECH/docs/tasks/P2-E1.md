## 1. What is asked

The Port Admin (`PORT_GM`) creates users with name, username, phone and a one-time password, and deactivates them. Nobody can deactivate themselves or the last active Port Admin, even if two admins try at the same time (`roadmap/roadmap-tasks.json:678-686`, `backend/atlantech_backend_tasks.md:80`). The task title also asks for the first Port Admin seeder.

**Done when** (each line is checkable by a test or a demo):

- [ ] `POST /users` creates a user (`is_active` 1, `must_change_password` 1) and returns a server-generated one-time password once, in that response only; the password is stored hashed, and appears in no audit row, log or later response.
- [ ] Creating a user above `license_states.max_users` is refused with 422 `PLAN_LIMIT_EXCEEDED` and nothing is saved; tug masters and pilots count as users (FR-AC-09, FR-LIC-04). No `max_users` (null or no row) means no limit.
- [ ] `POST /users/{user}/deactivate` sets `is_active` 0 under a row lock and the user is refused on the next request (`ACCOUNT_DISABLED`, existing `EnsureAccountUsable`). Allowed in READ_ONLY mode (FR-AC-10).
- [ ] Deactivating yourself → 409 `CONFLICT` (`errors.users.cannot_deactivate_self`); deactivating the last active Port Admin → 409 `CONFLICT` (`errors.users.last_port_admin`). Both are audited as `REJECTED_ATTEMPT`.
- [ ] Two admins deactivating each other (or two admins deactivating the last two admins) at the same time: exactly one succeeds, the other gets 409 or `ACCOUNT_DISABLED`; at least one active Port Admin always remains.
- [ ] `POST /users/{user}/activate` sets `is_active` 1 and runs the plan limit check (an inactive user does not count; activating counts as adding one).
- [ ] `GET /users` (paginated, filters `is_active`, `q`) and `GET /users/{user}` (with the active role and the role history) for P-23 and P-24.
- [ ] Every route sits in group `port.api`, declares `ability:users.manage`, and every update carries `version.token:user`. `RouteAbilityCoverageTest` stays green.
- [ ] `FirstPortAdminSeeder` creates the first Port Admin from `.env` values (no secret in a tracked file), only when no active `PORT_GM` exists.
- [ ] Every create, update and refusal is audited (FR-GL-02); OpenAPI, the error catalogue (CT-01) and the readiness pack are updated.

**Out of scope:** assigning or ending roles (P2-E2); devices and tokens (P2-E3); the full licence guard, READ_ONLY allow-lists and plan limits for terminals and berths (P2-D5); password change (done, P1-C2); editing name or phone after creation (not asked by FR-AC-09..13, the lead can add it later); deleting a user (never: rows are not deleted).

## 3. Design

### Endpoints

All in group `port.api`; role `PORT_GM` only (`ability:users.manage`); no terminal scope.

| Method and path | Request | Success | Errors (code) |
| --- | --- | --- | --- |
| `GET /users` | `page`, `per_page`, `is_active`, `q` (name or username) | 200 paginated list: `id`, `name`, `username`, `phone`, `is_active`, `must_change_password`, `version`, `created_at`, `active_role` | 401, 403 |
| `GET /users/{user}` | none | 200 the same plus `role_history[]` (all assignments, newest first: `role`, `organization_unit_id`, `unit_type`, `terminal_id`, `active_from`, `active_to`) | 401, 403, 404 |
| `POST /users` | `name` (≤120), `username` (3–50, lowercase letters, digits, `.`, `_`, `-`, unique), `phone` (optional, ≤30) | 201 the user + `one_time_password` (shown once) | 401, 403, 422 `VALIDATION_FAILED`, 422 `PLAN_LIMIT_EXCEEDED` |
| `POST /users/{user}/deactivate` | `version` | 200 the user (new `version`) | 401, 403, 404, 409 `VERSION_CONFLICT`, 409 `CONFLICT`, 422 |
| `POST /users/{user}/activate` | `version` | 200 the user | 401, 403, 404, 409 `VERSION_CONFLICT`, 422 `PLAN_LIMIT_EXCEEDED` |

Deactivate and activate repeat on an already-inactive or already-active user as a no-op that returns 200 with the same `version` (no audit row).

### Data

- Written: `users` (insert, update `is_active`), `audit_logs`. Read: `license_states.max_users`, `user_role_assignments` (active PORT_GM count), `organization_units`. Owner: Backend (CT-15).
- Migrations: none (columns and checks exist). `schema.sql` (CT-17) unchanged.
- New: `ErrorCode::Conflict` (`CONFLICT`, 409, `errors.conflict`) and message keys `errors.users.cannot_deactivate_self`, `errors.users.last_port_admin`. Not a database enum; not in the status vocabulary (CT-21).
- Rules in code: username lowercase (FormRequest lowercases before validating; the database CHECK is the backstop); last-Port-Admin count; plan limit.

### Behaviour

- **One-time password:** generated on the server (20 characters, letters and digits, `Str::password`-style, no look-alikes), hashed by the `hashed` cast, `must_change_password` 1. The raw value exists only in the controller response. `AuditService` already excludes `password_hash`; the test proves the audit row and logs never hold the raw value.
- **Plan limit seam:** a small interface in Shared (`UserLimitCheck::assertCanAddActiveUser()`, throws 422 `PLAN_LIMIT_EXCEEDED`) implemented in License (reads `license_states.max_users`, counts `users.is_active = 1`, inside the caller's transaction, locking the `license_states` row `FOR UPDATE` so two creates cannot both take the last seat). Bound in `LicenseServiceProvider`. Access calls the interface, never License (module order Shared < Access < License). P2-D5 extends the implementation.
- **Write chain order (P2-D2):** auth · password gate · `ability` · (`terminal.scope` n/a) · app version · licence mode · binding · `version.token` (middleware, early check) · FormRequest validation · business rules (self, last Port Admin) · plan limit (create and activate). Plan limits are last.
- **Deactivate, one transaction (`AuditService::transaction`):** lock `users` rows `FOR UPDATE` in id order for {target} ∪ {users holding an active `PORT_GM` assignment}; re-check the version on the locked target (`VersionToken::lockAndAssert`); then rule 1: target is the actor → 409; rule 2: target holds an active `PORT_GM` and no other locked admin has `is_active` 1 and an active `PORT_GM` assignment → 409; else set `is_active` 0, `recordUpdated`. Locking the whole admin set in id order serialises two admins deactivating each other (the second waits, then sees the first's result) and cannot deadlock.
- **Refusals:** after the transaction rolled back, `AuditService::rejectedAttempt(route, ErrorCode::Conflict, reason, actorId, username, 'users', targetId)` with reasons `cannot_deactivate_self`, `last_port_admin`, then the 409 problem is thrown.
- **Audit:** CREATE on `users` (actor = Port Admin); UPDATE on `users` (`is_active` before/after) for deactivate and activate; refused attempts as above.
- **Licence mode:** deactivate is allowed in READ_ONLY (FR-AC-10). The READ_ONLY allow-list belongs to P2-D5; the route is marked in the plan (and with a code comment) so D5 puts `users.deactivate` on the allow-list. Create and activate follow the normal write rules (blocked in READ_ONLY once D5 fills the hook).
- **Events and messages:** none. Sessions of the deactivated user end on their next request (existing gate); a mobile token of a deactivated user is revoked by `EnsureAccountUsable` on its next use (P1-C3 review). Revoking the devices and all tokens at once belongs to P2-E3.

### First Port Admin seeder

- `FirstPortAdminSeeder` (in `DatabaseSeeder`, every environment, before the demo seeders). Reads `config('seeding.first_port_admin')` = `FIRST_PORT_ADMIN_USERNAME`, `FIRST_PORT_ADMIN_NAME`, `FIRST_PORT_ADMIN_PASSWORD` from `.env` (keys listed empty in `.env.example`; values never in a tracked file).
- Runs only when all three are set and no user holds an active `PORT_GM` assignment; otherwise it prints one line and does nothing (idempotent). Creates the `HARBOUR_AUTHORITY` organization unit if missing (`firstOrCreate`; production has none, the demo seeder creates it only outside production), the user with `must_change_password` 1, and the `PORT_GM` assignment, in one transaction with a CREATE audit row (actor NULL = system). Never prints the password.
- With the demo seeders (B6, merged): demo `port.gm` is separate and never runs in production unless `SEED_DEMO_PORT=true`; if both exist there are two Port Admins, which is fine. If a real user already has a demo username the demo seeder gives them a demo role (B6 review N3); the first-admin username should not be `port.gm` (documented in `.env.example`).
