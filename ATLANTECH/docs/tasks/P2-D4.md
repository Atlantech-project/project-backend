## 1. What is asked

Stop two people overwriting each other: every editable record returns a `version`; an update sends the `version` it last read; a stale one is refused with 409 and the current data (`roadmap/roadmap-tasks.json:666-674`). The token is the record's `updated_at` as `DATETIME(6)`, returned as an opaque string (DEC-57 Closed; CT-01 §5).

**Done when** (each line is checkable by a test or a demo):

- [ ] `VersionToken` gives the one output format (`2026-11-02T10:15:04.123456Z`, UTC, microseconds) for a model's `updated_at`; resources use it for the `version` member.
- [ ] Middleware `version.token:<routeParam>` (the D2 hook, same class and position) on a write: reads `version` from the JSON body, compares it with the bound record's token, answers 409 `VERSION_CONFLICT` with `current: { id, version }` when they differ. It runs after `ability`, `terminal.scope`, 426 and 423, before the business rules (FR-GL-01, the order D2 pinned).
- [ ] A missing or malformed `version` answers 422 `VALIDATION_FAILED` with `errors.version` (`validation.required` / `validation.regex`) (lead's answer Q2). It is checked after the earlier steps, so an unauthorised caller never sees it.
- [ ] Race safety: the endpoint re-checks inside its transaction on the locked row (`VersionToken::lockAndAssert`: `SELECT … FOR UPDATE`, then the same comparison), so of two simultaneous writes with the same token exactly one commits and the other gets the same 409 (NFR-CONC-1 test shape: one wins, the other 409).
- [ ] After a successful write the record's token changes (a new `updated_at`), and the response carries the new `version`.
- [ ] A coverage test fails when a `PUT` or `PATCH` route in `routes/api.php` lacks `version.token` and is not on a short allow-list (empty today), so a later update endpoint cannot skip the check.
- [ ] Pint clean; full Pest suite green including `ModuleArchitectureTest` and `OpenApiDriftTest`.

**Out of scope:**

- The endpoints that use it (P2-E1.., P2-F1..F5); each adds `version.token:<param>` and returns `version`.
- The audit row for a refused 409 (FR-GL-02): needs the audit service of P2-D3 (Mariam, not merged). Section 7 records the gap; D3 adds the call in one place.
- Mobile idempotency (`Idempotency-Key`, CT-01 §4) and sync conflict handling (CT-07, P5-O2).
- Adding `updated_at` columns: the 24 migrations with `updated_at DATETIME(6)` already cover the tables the screens edit (checked in step 1; a table that lacks it is reported, not migrated here).

## 3. Design

### Names other tasks use

| Name | Where | Used by |
| --- | --- | --- |
| `VersionToken::of(Model): string`, `::matches(Model, string): bool`, `::rules(): array`, `::assertCurrent(Model, string): void`, `::lockAndAssert(Model, string): Model` | `app/Modules/Shared/Support/VersionToken.php` | every resource (`'version' => VersionToken::of($this->resource)`), every update service |
| Middleware alias `version.token:<routeParam>` → `EnsureRecordVersion` (body filled) | `app/Modules/Shared/Http/Middleware/EnsureRecordVersion.php` | every update route: `->middleware('version.token:user')` |

`VersionToken` lives in Shared (the shared kernel names "the version token" in its provider doc); it imports no other module.

### Endpoints

None. The middleware and helper are used by later routes.

| Method and path | Role(s) and scope | Request | Success | Errors (code) |
| --- | --- | --- | --- | --- |
| (no new route) | — | update requests carry `version` in the JSON body | the record with its new `version` | 409 `VERSION_CONFLICT` (+ `current`), 422 `VALIDATION_FAILED` (missing or malformed `version`) |

### Data

- Tables: none written. Token column: `updated_at DATETIME(6)` on each editable table (owner: Backend, CT-15). Migrations: none. `schema.sql` (CT-17): unchanged.
- Enums: none. `ErrorCode::VersionConflict` exists.
- Rules enforced in code: stale write refused; the compare is exact string equality of the formatted value, so clients must send back what they received (CT-01 §5).

### Behaviour

- Write chain step 6 (D2 order): after auth, password gate, ability, terminal scope, 426, 423 and route binding; before business rules and plan limits. Applies to writes only (`POST`, `PUT`, `PATCH`, `DELETE`); a route opts in by declaring the alias. Creating a record has no version.
- Two checks, one comparison function: the middleware answers early on the bound record (fast 409, correct position in the order); the endpoint re-checks on the locked row inside its transaction (`lockAndAssert`; it throws `LogicException` outside a transaction, so a service cannot forget the transaction). This closes the window between the middleware read and the save.
- A save that changes no column does not change `updated_at` (Eloquent skips it); the token stays and the response repeats it. A real change always produces a new token.
- Audit: none in this task (section 7). Licence mode: not involved in the check; the 423 step runs before it.
- Events and messages: none.

## 7. Conflicts and risks

| Finding | Sources that disagree | Proposed resolution | Decided by |
| --- | --- | --- | --- |
| NFR-CONC-1 says an integer `version` / `ETag`; FR-GL-05 and DEC-57 say `updated_at` | `Non Functional Requirements.md:96` vs `Functional Requirements.md:91` and DEC-57 | `updated_at DATETIME(6)` as an opaque `version` string (DEC-57 Closed wins) | DEC-57 (Closed) |
| A middleware compare alone is not race-safe (NFR-CONC-1: exactly one of two simultaneous writes commits) | NFR-CONC-1 vs a middleware-only design | Middleware for the order plus a locked re-check in the transaction | Marwan, 2026-11-03 (Q1) |
| CT-01 does not say what a missing or malformed `version` returns | CT-01 §5 vs §6 | 422 `VALIDATION_FAILED` with `errors.version` | Marwan, 2026-11-03 (Q2) |
| FR-GL-02 says every refused attempt is audited, but the audit service (P2-D3) is not merged | FR-GL-02 vs D3 status | D4 writes no audit row for the 409 now. D3's service (relayed 2026-11-03: `App\Modules\Shared\Audit\AuditService::rejectedAttempt(string $route, ErrorCode $code, string $reason, ?int $actorId, ?string $username, string $entityType = 'users', ?int $entityId = null)`, in Shared, own transaction, so it must be called after the refused write rolled back; branch `feature/P2-D3-audit-service`, tip `e53ae6a`, unmerged) is called from the `version.token` middleware and from the endpoint's catch after rollback, with `$entityType` = the table and `$entityId` = the row id, once D3 is merged. `assertCurrent` itself stays pure, because inside the locked transaction the audit would roll back with it. The gap stays until D3 merges. **Proposed by the plan; the lead may ask for a temporary `recordRejectedAttempt` call instead** | Plan (proposed) |
| Two writes in the same microsecond could get the same `updated_at` | Coding Notes §4 | Practically impossible with `DATETIME(6)` and the row lock; accepted | Plan |
| Security and concurrency task | — | **Recommendation: consider Opus for the final review before merge.** The lead decides | Marwan |
