## 1. What is asked

The Port Admin sees each user's registered devices, cancels one device or all of them (for example when a tablet is lost), and can undo the cancelling of one device (added 2026-11-06: the Mobile Team shows "sign-in stays available in case the admin restores the device", CT-04 v1.2) (`roadmap/roadmap-tasks.json:704-712`, `backend/atlantech_backend_tasks.md:82`). Done when a cancelled device can no longer act. FR-AC-13 (`requirements/Functional Requirements.md:135`): list devices, revoke one or all sessions; this does not close the VPN (Port IT, in the MDM).

**Done when:**

- [ ] `GET /users/{user}/devices` lists the user's devices with platform, app version, last seen, revoked date, whether push is registered and the number of live tokens.
- [ ] `POST /users/{user}/devices/{device}/revoke` sets `revoked_at` on the device, clears its push registration, and sets `revoked_at` on all live tokens of that device (`personal_access_tokens.user_device_id`). Nothing is deleted.
- [ ] `POST /users/{user}/devices/revoke-all` does the same for every non-revoked device of the user and for every other live mobile token of the user.
- [ ] After a revoke, a Bearer request with that device's token answers 401, and a new sign-in from that device is refused with 403 `DEVICE_REVOKED` (the C3 behaviour, proven by a test here).
- [ ] `POST /users/{user}/devices/{device}/restore` clears `revoked_at` on that device row, so it is a normal device again. It does **not** bring back any token: the tokens revoked with the device stay revoked (`personal_access_tokens` is untouched), so the old token still answers 401 and the user signs in again; that sign-in now succeeds (200 instead of 403 `DEVICE_REVOKED`). The push registration stays empty until the app registers it again. Restoring a device that is not revoked is a no-op (200); a device of another user → 404. Audited in the same transaction.
- [ ] Revoking again is a no-op (200). A device of another user addressed under this user → 404.
- [ ] Revoke and revoke-all are allowed in READ_ONLY mode (lead's answer); restore is a normal write, blocked in READ_ONLY once P2-D5 fills the hook (plan default, section 7 C8). Every change is audited in the same transaction. The push token never appears in a response or an audit row.
- [ ] OpenAPI and the readiness pack are updated.

**Out of scope:** web sessions: revoke-all does not touch the `sessions` table (lead's answer: mobile tokens only; use deactivate to end a user); bringing revoked tokens back (restore never does); device registration and push-token refresh (P1-C3, P5-N1); the VPN.

## 3. Design

### Endpoints

Group `port.api`, `ability:devices.manage`. `{device}` is bound scoped to `{user}` (a device of another user → 404, after the ability check). No `version.token`: `user_devices` has no `updated_at` and the actions are idempotent. These are Port Admin (web) routes; if a Bearer caller used them the mobile `Idempotency-Key` rule (IDEMP-01) would apply and their OpenAPI operations would list the header like any Bearer write.

| Method and path | Request | Success | Errors (code) |
| --- | --- | --- | --- |
| `GET /users/{user}/devices` | `page`, `per_page` | 200 paginated `UserDeviceResource`: `id`, `device_id`, `platform`, `app_version`, `last_seen_at`, `revoked_at`, `has_push_token`, `live_token_count` | 401, 403, 404 |
| `POST /users/{user}/devices/{device}/revoke` | none | 200 `UserDeviceResource` (revoked) | 401, 403, 404 |
| `POST /users/{user}/devices/revoke-all` | none | 200 `{ devices_revoked, tokens_revoked }` | 401, 403, 404 |
| `POST /users/{user}/devices/{device}/restore` | none | 200 `UserDeviceResource` (`revoked_at` null, `live_token_count` 0 until the user signs in again) | 401, 403, 404 |

Roles: `devices.manage` is held by `PORT_GM` only (`RolePermissions`), so all four routes are Port Admin only; every other role gets 403.

### Data

- Written: `user_devices` (on revoke: `revoked_at` set and `push_token`, `push_token_updated_at` NULL; on restore: `revoked_at` NULL), `personal_access_tokens` (`revoked_at`), `audit_logs`. Read: the same. Owner: Backend (CT-15). No migration here (C3 creates the table); `schema.sql` unchanged by this task.
- Rules in code: a revoked device must have `push_token` NULL (`chk_ud_push_revoked`), so the update clears the push fields in the same statement.
- Live token = `revoked_at IS NULL` (expired tokens are not counted as live either: `expires_at` null or in the future).

### Behaviour

- **Order (P2-D2):** auth · password gate · `ability:devices.manage` · binding (scoped) · rules. No version token, no plan limit.
- **Revoke one (`AuditService::transaction`):** lock the `user_devices` row `FOR UPDATE`; if `revoked_at` is already set → return it (no-op, no audit); else set `revoked_at = now`, clear the push fields, `UPDATE personal_access_tokens SET revoked_at = now WHERE user_device_id = ? AND revoked_at IS NULL`; audit UPDATE on `user_devices` (before/after `revoked_at`, and `tokens_revoked` in the `after_state` through `AuditService::record`).
- **Revoke all:** one transaction; lock the user's non-revoked device rows in id order; revoke each as above; then revoke the remaining live tokens of the user that have no device (`tokenable_type` = User, `tokenable_id` = user, `user_device_id` NULL); one audit UPDATE per device, and one UPDATE row for `personal_access_tokens` (entity id NULL) when tokens without a device were revoked. Returns the counts. Web sessions untouched.
- **Restore (`AuditService::transaction`):** lock the `user_devices` row `FOR UPDATE`; if `revoked_at` is null → return it (no-op, no audit); else set `revoked_at = null` and call `AuditService::recordUpdated` (UPDATE on `user_devices`, before/after `revoked_at`; the push token is hidden so it is not in the states). Tokens are not touched: revoke already revoked them in the same transaction (and `EnsureTokenDevice` revokes a stray one on use), so none can come back. The push fields stay NULL (`chk_ud_push_revoked` only forces NULL while revoked). Allowed for a deactivated user's device and for the admin's own.
- **Cancelled device cannot act:** `EnsureTokenDevice` refuses (401) a token that is revoked or whose device row is revoked, and `MobileSignInService` refuses the device at sign-in (`DEVICE_REVOKED`, audited). Revoking the tokens explicitly in the same transaction is still required (otherwise a token is only revoked when next used, and a restore in between would revive it). This task proves both end to end, and after a restore proves the old token is still 401 and a new sign-in is 200.
- **Revoking your own devices** is allowed. Deactivated users' devices can be revoked.
- **Licence mode:** revoke and revoke-all are allowed in READ_ONLY (lead's answer); P2-D5 puts `devices.revoke` and `devices.revoke-all` on the allow-list. Restore is not on it (it widens access). Until D5 the hook is a pass-through.
- **Events and messages:** none (no push is sent to a revoked device).
