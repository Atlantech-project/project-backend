## 1. What is asked

Field users sign in from the tablet: the device is registered, an outdated app is told to update, and the user gets a token that stays valid while in use (`backend/atlantech_backend_tasks.md:55`; roadmap: "Done when a tablet can sign in and an outdated app is refused").

**Done when:**

- [x] `POST /api/v1/auth/mobile/login` with `{username, password, platform}` and the headers `X-App-Version`, `X-Device-Id` answers 200 `{token, expires_at, user}` (CT-04 v1.1).
- [x] Missing or malformed headers → 422 `VALIDATION_FAILED`; then `X-App-Version` below `min_app_version` → 426 `APP_UPDATE_REQUIRED` with `min_app_version` and no token; then the body → 422 (D3).
- [x] 429, 401 and 403 `ACCOUNT_DISABLED` exactly as the web sign-in (shared `SignInService`), audited the same way.
- [x] A device with `revoked_at` set is refused with 403 `DEVICE_REVOKED`, audited, and no token is made (L2; **needs the CT-04 change**).
- [x] The `user_devices` row is created or updated (platform, app version, `last_seen_at`) per user and device; `last_seen_at` changes at sign-in only (D10).
- [x] `personal_access_tokens` exists with `revoked_at` and `user_device_id` (L5); the token is named with the device id; a new sign-in on the same device revokes the old token (D4); no token row is ever deleted.
- [x] Each use moves `expires_at` to 30 days from that use; an expired, revoked or unknown token answers a clean 401.
- [x] Signed-in routes accept the Bearer token (`port.api` uses `auth:sanctum`); a missing `X-Device-Id` on a Bearer request → 422, a different one → 401 (D6).
- [x] `EnsureMinAppVersion` compares `X-App-Version` (`x.y.z`, compared as versions) with `min_app_version` on every request that carries the header (P2-D2 Q2); a malformed one → 422.
- [x] Password gate and `POST /api/v1/auth/change-password` work with the Bearer token; other tokens stay valid after a change (D8).
- [x] A deactivated user's token gets 403 `ACCOUNT_DISABLED` and is revoked (Q-C3-3).
- [x] Web tests stay green after `auth:web` → `auth:sanctum`.
- [x] OpenAPI 1.4.0 (path, schemas, `DEVICE_REVOKED`, `bearerAuth` on the signed-in paths); `schema.sql` regenerated (CT-17); Pint and the full suite pass.

**Out of scope:** revoking the token on logout (P1-C4) · listing and revoking devices (P2-E3) · FCM push token (post-MVP) · the full chain (P2-D2, done).

## 3. Design

### Endpoints

| Method and path | Role(s) and scope | Request | Success | Errors (code) |
| --- | --- | --- | --- | --- |
| `POST /api/v1/auth/mobile/login` (`auth.mobile.login`) | Guest | headers `X-App-Version`, `X-Device-Id`; `{username, password, platform}` | 200 `{token, expires_at, user}` | 422 · 426 · 429 · 401 · 403 `ACCOUNT_DISABLED` · 403 `DEVICE_REVOKED` |
| `GET auth/me`, `POST auth/change-password`, `POST auth/logout`, `GET audit-logs` | unchanged | now also `Authorization: Bearer` | unchanged | + 422 / 401 for `X-Device-Id`, 426 for an old `X-App-Version` |

### Data

- New table `personal_access_tokens` (Sanctum, Backend-owned, never deleted): Sanctum's columns plus `user_device_id` (FK `user_devices`, L5) and `revoked_at`. Datetimes are `DATETIME` like the port tables. Workers get no grant (framework table, like `sessions`).
- Writes `user_devices` (create or update) and `personal_access_tokens`. No change to `users` or `user_role_assignments`.
- New error code `DEVICE_REVOKED` 403 (Q-C3-1).

### Behaviour

- Order on mobile sign-in, by route middleware then the controller: `EnsureMobileHeaders` (422) → `EnsureMinAppVersion` (426) → `MobileLoginRequest` (422) → `SignInService` (429, 401, 403) → revoked device (403) → device row and token.
- `App\Modules\Shared\Support\AppVersion`: the `x.y.z` rule and the comparison (`version_compare`), in one place.
- `EnsureMinAppVersion` reads `MinAppVersionSource` (P1-C5); 503 when the setting is missing.
- `App\Modules\Access\Models\PersonalAccessToken` extends Sanctum's: the slide (`expires_at` = `last_used_at` + 30 days whenever Sanctum stamps `last_used_at`), `revoke()`, and `delete()` refused. Sanctum's token check also refuses `revoked_at`.
- `EnsureTokenDevice` (right after authentication, Bearer requests only): missing `X-Device-Id` 422, other device 401.
- `port.api`: `auth:web` → `auth:sanctum`. Sanctum tries the web session first, then the token.
- Audit: 401 and 403 through the existing paths; `DEVICE_REVOKED` through `AuditService::rejectedAttempt` with the user as actor and the device as entity; no row for a success or a 426 (Q10, D11).
- Licence mode: sign-in is not a write; 423 does not apply.
