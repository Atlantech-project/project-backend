## 3. Design

### Endpoints

None. No route, OpenAPI or SSE change.

### Data

- **Tables written** (all Backend-owned, CT-15): `port_profiles`, `port_settings`, `imdg_classes`, `container_size_types`, `vessel_types`, `cargo_types`, `yard_zone_types`, `storage_types`, `capability_types`, `equipment_categories`, `status_types`, `external_systems`, and for the demo port `organization_units`, `terminals`, `berths`, `berth_terminals`, `navigation_channels`, `channel_waypoints`, `port_shifts`, `users`, `user_role_assignments`, `pilot_profiles`, `pilot_schedules`, `tugboats`, `tug_master_profiles`, `tug_master_schedules`.
- **Migration (one):** `…_alter_port_settings_add_min_max.php` adds `min_value` and `max_value` as nullable `decimal(18,6)`-style columns (type to be confirmed in step 4, see Q-A). Nullable because `STRING`, `JSON` and `BOOL` keys have none. This touches `port_settings`, which the AI workers read: `ai-impact` label + one AI Team approval (CT-17 §6); check `database/grants/workers.sql` still covers the table; regenerate `schema.sql` (CT-17 §5). Not a rename or drop, so a minor version of CT-17.
- **Enums:** only existing P1-B5 enums (`PortSettingValueType`, roles, unit types, `TerminalType`, pilot rank, tug units). No CT-21 change.
- **Seeding rules** (CT-18 §3, Backend part): reference tables upsert by `code`; `port_settings` insert missing keys, update `setting_value` only while `updated_by IS NULL`, always update `description` / `min` / `max`.
- **Source file of the data:** `contracts/reference-seed.json` is a contract file and DEC-59 says the app must not depend on contract files in production. The seeder therefore reads a copy inside the app, `database/seeders/data/reference-seed.json`, and a test fails if that copy differs from `docs/reference/contracts/reference-seed.json` (so `sync-check` drift is caught).
- **Demo fixture:** `database/seeders/data/damietta-demo-port.json` holds the port profile, terminals, berths, channel, shifts, tugs and user lists as plain JSON, so AI-015 can read the same file. Berth rows obey `chk_berth_loa_fits` (`max_vessel_loa <= length`) and `depth_datum` equals the channel's (`LAT`). Berths per terminal sum to 36, over 8 terminals; terminal names are descriptive demo names (not real operators' contracts), codes such as `DCT`, `DIPCO`, `DCHC` for container terminals; at least one berth is shared by two terminals. Port profile: Damietta, `governorate_code` `DT`, `port_code` `EGDAM`, timezone `Africa/Cairo`, a fixed fake-but-valid `public_id` UUID constant (the real value comes from SaaS registry later).
- **People:** fake Arabic names from a fixed list in the fixture; usernames like `pilot.01`, `tugmaster.01`, `port.gm`; no real person. 12 pilots (ranks spread FIRST / SECOND / THIRD), 10 tugs (`BOLLARD_PULL_TONNES`) each with one tug master (`assigned_tugboat_id` unique), 12 demo role users in total plus the pilots and tug masters (pilot and tug master are two of the 12 roles).
- **Password:** `DEMO_USER_PASSWORD` from `.env` (added as an empty line to `.env.example`); `must_change_password = 1`; with no variable, `Hash::make(Str::random(40))`. The existing `test.user` of `DatabaseSeeder` stays.
- **Rules the database does not enforce, done in the seeder:** a TERMINAL organization unit per terminal; every berth has a `berth_terminals` row; pilot user holds `MARINE_PILOT` in MARINE_SERVICES and tug master holds `TUG_MASTER` (D-29); active shifts do not overlap (3 shifts of 8 hours: `00:00-08:00`, `08:00-16:00`, `16:00-00:00`; midnight end `00:00` is allowed by `chk_port_shift_times` and the "next day" note).

### Behaviour

- Write chain, audit, licence mode, transactions and events: not applicable (seeders run from the console, not through the API; no `audit_log` rows, no SSE, no jobs). Each seeder runs inside one DB transaction per seeder class so a half-seeded demo port cannot remain.
- `DatabaseSeeder` calls, in order: `PortProfileSeeder`, `PortSettingsSeeder`, `ReferenceDataSeeder`, then `DemoPortSeeder` only when `APP_ENV` is not `production` or `SEED_DEMO_PORT=true`. `test.user` is created once (`firstOrCreate`) so re-seeding does not fail on the unique username.
- Idempotent: running `db:seed` twice gives the same counts.
- Generated columns (`single_key`, `active_assignment_key`) are never written.
