## 1. What is asked

Check every pull request into `develop` automatically: code style (Pint) and the whole Pest suite against a real MySQL 8.4 and Redis, so a broken change is visible to the team before merge and a failing test stops a pull request from merging. (Lead decisions of 2026-10-28: no Larastan; runs on pull requests into `develop`, not on every push.)

**Done when** (each line is checkable by a CI run or a GitHub screen):

- [x] A pull request into `develop` (opened, synchronize, reopened, ready_for_review) starts the workflow `CI` with two jobs: `pint` and `tests`.
- [x] `pint` runs `vendor/bin/pint --test` (default Laravel preset; no `pint.json` exists) and fails on a style violation.
- [x] `tests` runs the full suite (`php artisan test`) including groups `schema` and `infra`, on MySQL 8.4 and Redis 7.4 service containers (the same images as `docker-compose.yml`), and passes; `ContractsSchemaTest` finds a `mysqldump`.
- [x] A pull request into `develop` with a failing test shows a red required check and cannot be merged (demo PR, closed afterwards).
- [x] The README shows the CI status badge for `develop`.

**Out of scope:** static analysis (Larastan/PHPStan; lead decision, section 7) · contract tests against the JSON Schemas (P3-I8) · coverage thresholds as a gate (NFR-EXT-4; question 6) · OpenAPI lint (P1-A4) · checking that PortHub's `contracts/db/schema.sql` is current (PortHub repository) · deployment pipelines (P6-R6) · the AI CI (AI-016) and the web CI (FE-012).

## 3. Design

### Endpoints

None.

### Data

- Tables: none changed. CI builds the schema from the migrations (`useSchemaDatabase()` runs `migrate:fresh`).
- Migrations: none.
- Databases on the CI MySQL service: `atlantech` (created by `MYSQL_DATABASE`, used by `InfrastructureTest`), `atlantech_testing` (created by a workflow step; `phpunit.xml` default and `DB_SCHEMA_TEST_DATABASE` default), scratch databases created and dropped by the tests (`atlantech_schema_test`, `atlantech_schema_rebuild`).

### Behaviour (the workflow)

- File: `project-backend/.github/workflows/ci.yml` (GitHub only reads workflows at the repository root). `defaults.run.working-directory: ATLANTECH`; cache keys use `ATLANTECH/composer.lock`.
- Triggers (question 3, lead): `pull_request` into `develop` only (types `opened`, `synchronize`, `reopened`, `ready_for_review`); no `push` trigger, not on `main`; `concurrency` per PR ref with `cancel-in-progress`, so a new push to the PR cancels the older run. Jobs skip draft PRs (`if: github.event.pull_request.draft == false`).
- PHP: `shivammathur/setup-php` with PHP 8.4 and the Dockerfile's extensions (`pdo_mysql, redis, intl, bcmath, pcntl, zip`), `coverage: none`; Composer cache; `composer install --no-interaction --no-progress --prefer-dist` (question 4: setup-php vs the Docker image).
- Job `pint`: no services; `vendor/bin/pint --test`.
- Job `tests`: services `mysql:8.4` (`MYSQL_ALLOW_EMPTY_PASSWORD: yes`, `MYSQL_DATABASE: atlantech`, port 3306, health check `mysqladmin ping`) and `redis:7.4-alpine` (port 6379, health check `redis-cli ping`), the same images and settings as `docker-compose.yml`. Steps: `cp .env.example .env`, `php artisan key:generate`, `mysql -h127.0.0.1 -uroot -e "CREATE DATABASE atlantech_testing"`, `php artisan test --compact`.
- Environment rule: the job does **not** set `DB_DATABASE` (a real environment variable wins over `phpunit.xml`'s `<env>`, so setting it would move the tests off `atlantech_testing`). `DB_HOST=127.0.0.1` and `REDIS_HOST=127.0.0.1` come from `.env.example`.
- `mysqldump`: the GitHub Ubuntu runner ships a MySQL client; `GenerateContractsSchema` finds it first. Risk in section 7 (client 8.0 against server 8.4).
- Composer script so developers run the same style check locally: `composer lint` (`pint --test`). No `composer analyse` (no Larastan).
- Visibility: GitHub marks the PR red; a status badge in `project-backend/README.md`.
- Gate: branch protection on `develop` only (CI does not run on PRs into `main`) requiring `pint` and `tests`, 0 approvals (step 5, lead).
- Write chain, transactions, audit, licence mode, events: not applicable.
