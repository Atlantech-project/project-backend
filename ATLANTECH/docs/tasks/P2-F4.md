## 1. What is asked

A CT Administrator manages their own terminal's equipment (quantities and capabilities) and the container yard from zones down to slots, with reefer, dangerous goods and OOG details. Roadmap done-when: "the full yard of a terminal can be entered". DEC-29 open item G-03 adds to this task: creating all slots of a block, and a Damietta demo yard.

**Done when:**

- [x] A `TERMINAL_ADMIN` creates, reads and updates equipment of their own terminal: category, quantity, maintenance quantity, blocked quantity, capabilities. `available_quantity` is returned and never accepted as input (FR-MD-11). *PR 1: `EquipmentApiTest` create, quantity and capability update, reads, `typed available quantity`.*
- [ ] The same user builds a yard: zones (with the detail their zone type requires: reefer plugs, DG allowed IMDG classes, OOG limits), blocks, and slots by bay, row and tier (FR-MD-12).
- [ ] All slots of a block are created in one request (DEC-29 G-03).
- [ ] Changing the block size adds the missing slots and removes the extra ones without touching the kept slots; a slot to remove that is occupied, referenced or `BLOCKED` refuses the whole request (Q8).
- [ ] An unused block or zone can be deleted, with a DELETE audit row; a used one answers 409 (Q8).
- [ ] A slot or a whole stack can be set `ACTIVE` or `BLOCKED` by the CT Administrator or the `TERMINAL_OFFICER` of that terminal (Q2); `container_id` is never writable.
- [ ] The `TERMINAL_OFFICER` reads their terminal's yard but gets 403 when creating or editing its structure.
- [ ] Zone capacity is computed from slots, not stored.
- [ ] Another terminal's equipment or yard answers 403 and writes `REJECTED_ATTEMPT` (FR-AC-15). *Equipment part proven in PR 1 (`keeps another terminal out…`); yard part in PR 2.*
- [ ] Equipment and yard writes on a `NON_CONTAINER` terminal answer 422 (Q5). *Equipment POST and PUT proven in PR 1; yard in PR 2.*
- [ ] Every write leaves an audit row in the same transaction; a stale `version` answers 409. *Equipment proven in PR 1 (create, update, capability sync, `answers 409…`); yard in PR 2.*
- [ ] Every new write route is in the `port.api` group, so the licence step applies to it. The 423 refusal itself is **not** provable yet: `EnsureLicenseAllowsWrite` is a pass-through until P2-D5. *Equipment routes proven in PR 1 (`puts both write routes in port.api…`).*
- [ ] A Damietta demo yard is seeded for the container terminals (`DCT`, `DIPCO`, `DCHC` in the demo data) (DEC-29 G-03).
- [ ] After CT-18 v1.2 is approved, the yard zone types include `EMPTY` (Q6).
- [ ] OpenAPI (CT-02) lists every new endpoint. *Equipment endpoints in 1.13.0, `OpenApiDriftTest` passes (PR 1).*

**Out of scope:** deleting container yards or equipment (Q8; a wrongly added equipment row has no removal, a gap) · irregular blocks with different stack heights (Q8 assumes regular blocks; no real layout seen) · `equipment_cargo_compatibilities` and `terminal_cargo_types` (Q3, a recorded gap) · Vue pages (FE-071, FE-072) · terminal productivity profile (P2-F6) · `ResourceChanged` dispatch for equipment (P2-F7, `docs/tasks/SHARED-01.md:32`) and its listener (P4-K5) · NCT storage facilities, warehouses, tanks and NCT equipment (FR-MD-17, P2, not MVP) · container placement and removal from the tablet, `yard_slot_events`, slot check at accept and export (DEC-29 G-02, G-06, Sprint 6) · two-slot representation for 40/45 ft (DEC-29 G-04) · yard run and recommendation endpoints (P6-P1 to P6-P3) · AI yard solver (AI-065 to AI-068).

## 3. Design

Follows the answers in section 8.

### What exists on `origin/develop`

Migrations, models and factories for `equipment_categories`, `equipment`, `equipment_capabilities`, `equipment_cargo_compatibilities`, `yard_zone_types`, `yard_zones`, `dg_zone_allowed_classes`, `oog_zone_details`, `reefer_zone_details`, `yard_blocks`, `yard_slots`, `storage_facilities`. Abilities `equipment.manage` and `yard.manage` exist and belong to `TERMINAL_ADMIN` only. `port-state.read` belongs to the port-wide office roles, `TERMINAL_ADMIN` and `TERMINAL_OFFICER` (`RolePermissions.php:68-77`, PortHub `contracts/role-matrix.md` v1.1). `ReferenceDataSeeder` seeds `yard_zone_types` (GENERAL, REEFER, DANGEROUS_GOODS, OOG), `capability_types` (4), `equipment_categories` (6), `storage_types` (4). No route, controller, service or OpenAPI path for equipment, yard or storage; no seeder creates a storage facility or a yard.

### Endpoints

All under `/api/v1/terminals/{terminal}` so that `terminal.scope` applies (it reads the `{terminal}` route parameter). Child records are resolved through the chain; a child of another terminal answers 404.

| Method and path (after the prefix) | Ability | Notes |
| --- | --- | --- |
| GET `equipment`, `equipment/{equipment}` | `port-state.read` | With capabilities, `available_quantity`, `version` |
| POST `equipment` · PUT `equipment/{equipment}` | `equipment.manage` | Capabilities sent as a full list inside the same body; one row per (terminal, category) |
| GET · POST · PUT `yards` (Q1) | read `port-state.read` · write `yard.manage` | Only `detail_kind = CONTAINER_YARD` |
| GET · POST `yards/{yard}/zones` · PUT `yard-zones/{zone}` | same | Zone and its detail (reefer / DG classes / OOG limits) in one body and one transaction |
| GET · POST `yard-zones/{zone}/blocks` · PUT `yard-blocks/{block}` | same | |
| GET `yard-blocks/{block}/slots` | `port-state.read` | Paginated; filters bay, row, tier, status |
| PUT `yard-blocks/{block}/layout` | `yard.manage` | Body bays, rows, tiers and the block `version` (Q8). Creates every position on an empty block (G-03); later adds missing and removes extra slots; kept slots are unchanged; new ones are `ACTIVE`. Upper limit on the total. Any slot to remove that has a container, is referenced (for example by `yard_placement_items`) or is `BLOCKED` → 409, nothing changes. Moves the block's `updated_at` |
| DELETE `yard-blocks/{block}` · DELETE `yard-zones/{zone}` | `yard.manage` | Only with `version`; block without slots and unreferenced; zone without blocks (detail rows removed in the same transaction); otherwise 409 |
| PUT `yard-slots/{slot}` | `yard-slot-status.update` | `status` only, with `version` |
| POST `yard-blocks/{block}/stack-status` | `yard-slot-status.update` | One bay and row, all tiers, one status (DEC-29 rule 11); slot rows locked in one transaction; any occupied slot refuses the whole request |
| GET reference lists (not under a terminal, so no `terminal.scope`): equipment categories, capability types | `port-state.read` | Read-only (Q6) |
| GET reference lists (same): yard zone types, and IMDG classes if no endpoint exists | `port-state.read` | Read-only (Q6) |

New ability (Q2; name proposed, fixed in step 7): `yard-slot-status.update` for `TERMINAL_ADMIN` and `TERMINAL_OFFICER`. Reading needs nothing new: both roles already hold `port-state.read`, and `terminal.scope` limits them to their own terminal.

Success: 200 for reads and updates, 201 for creates. Errors (existing codes): 401 `UNAUTHENTICATED`; 403 `FORBIDDEN` or `PASSWORD_CHANGE_REQUIRED`; 426 `APP_UPDATE_REQUIRED` (Bearer); 423 `LICENSE_READ_ONLY`; 404 `NOT_FOUND`; 409 `VERSION_CONFLICT`; 409 `CONFLICT` (inactive terminal for a terminal-scoped writer, blocking an occupied slot, a refused layout shrink or delete); 422 `VALIDATION_FAILED`. Duplicate codes (zone, block, equipment category): follow the P2-F2 convention, checked in step 1. `PLAN_LIMIT_EXCEEDED`: no plan limit for equipment or yard was found in the sources read.

### Data

- Written (Backend owned, AI reads, CT-15): `equipment`, `equipment_capabilities`, `yard_zones`, `reefer_zone_details`, `dg_zone_allowed_classes`, `oog_zone_details`, `yard_blocks`, `yard_slots` (position and `status` only), `storage_facilities` (container yard only, Q1).
- Read: `terminals`, `storage_types`, `yard_zone_types`, `equipment_categories`, `capability_types`, `imdg_classes`.
- Not touched: `equipment_cargo_compatibilities` (Q3), `yard_placement_items`.
- Migrations (Q7, PR 2): `updated_at DATETIME(6)` on `yard_zones` and `yard_blocks`; their models then enable the updated-at column (both are `timestamps: false` today). AI workers read these tables, so CT-17 §6 requires the PR to carry `ai-impact` and get one AI Team approval (additive, minor); update `database/grants/workers.sql` if the grants need it. `equipment`, `storage_facilities`, `yard_slots` already have the column.
- Enums (CT-21): existing `ZoneDetail`, `YardSlotStatus`, `EquipmentRole`; no new value expected.
- Rules enforced in code: terminal is `CONTAINER` (Q5); zone detail matches the zone type, `zone_detail` and `detail_kind` are set by the server and never sent; zone type of an existing zone cannot change; reefer needs `total_power_plugs > 0`; DG needs at least one IMDG class; OOG limits are optional and positive; `maintenance_quantity + blocked_quantity <= quantity`; capability type unique per equipment; block `slot` positions positive and unique; only an empty slot can be blocked. The database CHECKs stay as the backstop; the request returns 422 before reaching them.

### Behaviour

- Write chain: auth · password gate · ability and terminal scope · app version (Bearer) · licence mode · version token · rules. `Idempotency-Key` for Bearer writes through the existing middleware.
- Transactions and locks: one `AuditService::transaction` per write; zone with detail and equipment with capabilities are atomic. Layout change, block delete and stack status lock the block row first, so two requests cannot interleave; the layout change also locks the slots it will remove before checking them.
- Version: the parent's `version` covers its detail rows (capabilities → equipment; zone details → zone). A child-only change must still move the parent's `updated_at`.
- Audit: CREATE / UPDATE / DELETE in the same transaction (`AuditLogAction::Delete` exists; confirm `AuditService` writes it in step 6). A layout change writes one audit row for the block with the counts added and removed, not one per slot. Refused attempts as `REJECTED_ATTEMPT`.
- Licence: `EnsureLicenseAllowsWrite` is in `port.api` but only calls the next step (P2-D5 is not implemented), so READ_ONLY and SETUP block nothing yet. No allowlist tag on the new routes, so they are covered when P2-D5 lands. No licence code in this task.
- Patterns to copy (read in step 1, from P2-F2): thin controller with `Store…`/`Update…`/index requests and a resource that returns `VersionToken::of()`; service wraps each write in `AuditService::transaction()`, locks with `VersionToken::lockAndAssert()`, then `recordCreated` / `recordUpdated` / `recordDeleted`; duplicates are `unique` validation rules (422); fields that may not change are `prohibited`; lists use the request's `page()` and `TerminalScope`; an inactive terminal gives a terminal-scoped writer 409 from `terminal.scope`; messages live in `lang/en/errors.php`. For scoped bindings, `Terminal::equipment()` and `Terminal::storageFacilities()` exist; a `{yard}` route parameter would need its own relation name (settle in step 7). `.ai/rules` does not exist.
- Events: none sent by this task. P2-F7 dispatches `ResourceChanged(EQUIPMENT)`. No SSE, Reverb, notification or AI job.
- Modules: equipment in `app/Modules/MasterData`, yard in `app/Modules/Yard` (where the models are); `ModuleArchitectureTest` must stay green.
