## 1. What is asked

Every signed-in request is checked against the caller's one active role (DEC-36) and, for the three `TERMINAL_*` roles, against their terminal. A role that does not hold the ability a route needs gets 403 `FORBIDDEN`; a terminal-scoped user touching another terminal's record gets 403; a field user only ever reaches tasks assigned to them. Roadmap done-when: "a test for every role passes and out-of-scope requests are refused" (`roadmap/roadmap-tasks.json:633`).

There is no role-to-function matrix in the documents (only prose in `Users & Actors.md`), so this task also writes it (lead's choice, Q1) from the responsibilities of each role, grouped by function area. Each later endpoint declares the ability it needs.

**Done when** (each line is checkable by a test or a demo):

- [ ] `Ability` enum (28 values, grouped by function area) and `RolePermissions` matrix cover all 12 roles (`MARINE_SAFETY_OFFICER` holds no ability in this task, see section 7); the matrix test checks 12 roles × every ability against an expected table written in the test, so any change to the matrix shows in the diff.
- [ ] Middleware `ability:<name>` answers 403 `FORBIDDEN` when the role does not hold the ability, 401 for a guest (the 401 stays first), and runs after the password gate (`EnsureAccountUsable`) in the fixed order of FR-GL-01.
- [ ] A user with no active role: 200 on `auth/me`, `auth/change-password` and `auth/logout` (they have no `ability:` middleware), 403 on every route that declares an ability (answer N2 of P1-C1).
- [ ] Terminal scope: middleware `terminal.scope` refuses a `TERMINAL_*` user whose route `{terminal}` is not their terminal (403); port-wide roles pass. A helper does the same for ids in a body or query and restricts list queries to the user's terminals. Another terminal's record answers 403, not 404 (Q2).
- [ ] Field users (`MARINE_PILOT`, `TUG_MASTER`, `TERMINAL_SUPERVISOR`) hold only the own-task abilities (and `terminal-status.update` for the supervisor, own terminal) and no web or admin ability (DEC-48). An own-task scope on `plan_components.assigned_user_id` returns only the caller's tasks; another user's task answers 403.
- [ ] Every refused role, terminal or own-task check writes a `REJECTED_ATTEMPT` audit row through `SignInService::recordRejectedAttempt` (the method used by the password gate), with route, status 403, code `FORBIDDEN` and a reason (`no_active_role`, `role_not_allowed`, `terminal_out_of_scope`, `not_own_task`). One class (`AccessRefusal`) calls it so P2-D3 replaces it in one place.
- [ ] A security-matrix test runs at least 30 distinct cross-role unauthorized calls and all are 403 (NFR-SEC-2).
- [ ] A coverage test fails when a route in `routes/api.php` has neither an `ability:` middleware nor an entry in the allow-list (login, csrf, `auth/*`), so a later endpoint cannot be added unprotected.
- [ ] The role matrix is published for Frontend and QA as `contracts/role-matrix.md` in PortHub from a Backend command (Q9), paired PR.
- [ ] Pint clean; full Pest suite green including `ModuleArchitectureTest` and `OpenApiDriftTest`.

**Out of scope:** the other write-chain steps and their order (P2-D2) · the audit service (P2-D3 replaces `recordRejectedAttempt`) · the endpoints that use the abilities (P2-E1, P2-F1..F5, later phases) · the "CT only" and "Non-Container only" checks on equipment, yard and safety constraints (the endpoint's rule, section 7) · the full My tasks list and `GET /sync/changes` (P5-O1 extends the scope built here) · SaaS Admin access (P7-S1, its own guard; FR-AC-17) · web screens (P-20, FE-021/022) · mobile sign-in (P1-C3).

## 3. Design

### Names other tasks use

| Name | Where | Used by |
| --- | --- | --- |
| `Ability` (string-backed enum, e.g. `users.manage`) | `app/Modules/Access/Enums/Ability.php` | every later endpoint, test and the published matrix |
| `RolePermissions` (`abilitiesFor(Role)`, `allows(Role, Ability)`) | `app/Modules/Access/Services/RolePermissions.php` | middleware, Gate, matrix command and test |
| `Role::isTerminalScoped()`, `Role::isFieldRole()` | `Role` enum (new methods) | scope helpers, profile |

| Route middleware alias `ability` (`->middleware('ability:users.manage')`) → `EnsureAbility` | `app/Modules/Access/Http/Middleware/EnsureAbility.php` | P2-D2 chain step "role and terminal scope", every route |
| Route middleware alias `terminal.scope` → `EnsureTerminalScope` (route parameter `{terminal}`) | `app/Modules/Access/Http/Middleware/EnsureTerminalScope.php` | terminal routes (P2-F2, P2-F4, P3-H4, P6-P2) |

| `AccessRefusal::refuse(Request, User, reason)` (audit + throw 403) | `app/Modules/Access/Services/AccessRefusal.php` | the two middleware and the helpers; the one place P2-D3 changes |
| Gate: one `Gate::define` per ability in `AccessServiceProvider` | same provider | `$user->can('users.manage')`, policies, `authorize()` |

Order on a signed-in route: `auth:web` → `EnsureAccountUsable` (password gate) → `ability:…` → `terminal.scope`. P2-D2 puts these in one named group in this order.

Own tasks is a **local scope**, not a global one: workers, jobs and the dispatcher must still read all components. Access never imports Plan; `PlanComponent` uses the trait.

### Endpoints

None. Only middleware, services and the matrix. Existing `auth/*` routes keep their stack.

### Data

- Tables read: `users`, `user_role_assignments` (active row, `active_to` NULL), `organization_units` (`terminal_id`), `plan_components` (`assigned_user_id`, `terminal_id`, scope only). Written: `audit_logs` (insert only, `REJECTED_ATTEMPT`). Owners per CT-15: Backend for all of these.
- Migrations: none. `schema.sql` (CT-17) unchanged.
- Enums: new `Ability` (not a database value, not in the status vocabulary CT-21). `Role` gets two methods only.
- Rules enforced in code (not by the database): role holds the ability; terminal-scoped user acts only on their terminal; a field user reads and updates only components where `assigned_user_id` is theirs.

### Behaviour

- Write chain steps that apply: "role and terminal scope" (second step after auth and the password gate). The remaining steps are P2-D2.
- Transaction and locks: none for the check. The audit row is inserted by `recordRejectedAttempt` in its own transaction before the 403 is thrown.
- Audit: `REJECTED_ATTEMPT`, `actor_id` = the user, `entity_type` `users`, `entity_id` = the user, `after_state` `{route, status 403, code FORBIDDEN, reason, username}` (the existing shape). Reasons: `no_active_role`, `role_not_allowed`, `terminal_out_of_scope`, `not_own_task`. Reads that are refused are audited too (FR-GL-02).
- Licence mode: not involved (role check comes before the 423 step); allowed in every mode.
- Events and messages: none.
- Channel: the checks read `$request->user()` and do not depend on the guard, so Mona's mobile sign-in (P1-C3, token guard) works with the same middleware.
- Field roles on the web (DEC-48): sign-in and `auth/me` still answer 200 so the web can show P-20; every other web ability is missing, so everything else is 403.
