## 1. Document Purpose & Scope

### 1.1 Purpose

This document specifies the Non-Functional Requirements (NFRs) for **ATLANTECH** and serves as the binding quality-attribute contract for system architecture, database design, security auditing, and technical evaluation[cite: 4, 6]. All requirements satisfy SMART criteria: Specific, Measurable, Achievable within a functional prototype deployment, Relevant to maritime coordination, and operationally qualified[cite: 6].

### 1.2 Scope

| Component | Phase | Description |
| :--- | :--- | :--- |
| Unified Port Data Model | Phase 1 | Core entity model for vessels, berths, tugs, pilots, cargo[cite: 6] |
| Marine Resource Recommendation Engine | Phase 1 | Vessel sequencing, berth/tug/pilot allocation algorithms[cite: 6] |
| State Tracking & Deviation Log | Phase 1 | Plan vs. actuals comparison, deviation recording[cite: 6] |
| Notification & Dispatch Service | Phase 1 | Scheduled plan dispatch and reminders[cite: 6] |
| Container Terminal Coordination Module | Phase 2 | Yard-placement & operational timing recommendations (Reference: Container Terminal Case Study)[cite: 4, 6] |
| Port-Agnostic Extensibility Framework | Phase 3 | New terminal & port onboarding without core codebase modification[cite: 6] |

## 2. Architectural Constraints & Critical Assumptions

Non-negotiable architectural constraints that govern the system design:

| Constraint | Statement |
| :--- | :--- |
| **C-1 Advisory Layer Only** | ATLANTECH is strictly a recommendation and coordination layer[cite: 4, 6]. It does not execute, override, or directly mutate downstream operational execution systems (e.g., Terminal Operating Systems [TOS] such as Navis N4, or Port Management Information Systems [PMIS] such as SPS-Harbor)[cite: 4, 6]. All NFRs apply exclusively to recommendation generation, data normalization, and coordination outputs[cite: 6]. |
| **C-2 Multi-Operator Confidentiality Boundary** | Commercial ports host competing terminal operators sharing public marine infrastructure (channel, tugs, pilots)[cite: 4, 6]. The system must enforce cryptographic and data-layer isolation: no terminal operator may access, query, or infer operational data, resource allocations, or cargo manifests belonging to a competing operator (Reference Case Study: Damietta Port — competing terminal operators)[cite: 4, 6]. |
| **C-3 Human-in-the-Loop Mandate** | No operational recommendation generated by the engine shall execute automatically[cite: 4, 6]. Every plan component requires explicit human approval (FR-1.4.6, FR-1.4.7, FR-2.2.5)[cite: 6]. Performance NFRs optimize for human decision latency rather than real-time machine-to-machine control loops[cite: 6]. |
| **C-4 Offline-First Field Operations** | Marine Pilots and Tug Masters operate in hostile, intermittent RF/cellular network conditions[cite: 6]. Field interfaces must function offline with deterministic, monotonic state-machine conflict resolution upon reconnection[cite: 6]. |
| **C-5 Open Standards Primacy** | Cargo manifest and vessel stowage data ingestion must comply strictly with the UN/EDIFACT BAPLIE standard[cite: 4, 6]. The parser must reject non-compliant files rather than introducing proprietary schema extensions[cite: 6]. |

## 3. Category 1 — Performance Efficiency

> **ISO/IEC 25010 Characteristic:** Performance Efficiency — Time Behaviour, Resource Utilisation, Capacity[cite: 6]

| NFR ID | Requirement Name & Scope | Quantitative Metric / Technical Constraint | Verification Method |
| :--- | :--- | :--- | :--- |
| **NFR-PERF-1** | Recommendation Engine Latency | p50 <= 3 s; p95 <= 8 s; p99 <= 15 s — measured from trigger receipt to complete recommendation payload generation under a concurrent load of 15 active Berthing Request pipelines (FR-1.4.1–FR-1.4.4)[cite: 6]. | Scripted load test (k6/Locust) injecting 15 simultaneous recommendation requests seeded with Damietta reference topology (36 berths, 8 active terminals, 20+ marine resources); 100 consecutive runs[cite: 6]. |
| **NFR-ENG-1** | Recommendation Engine Solver Timeout & Heuristic Fallback | Combinatorial optimization solver bounded by a strict **10-second circuit-breaker deadline**[cite: 6]. If the solver fails to converge within 10 s, the engine must abort the optimization loop, invoke a deterministic Rule-Based FIFO heuristic, and return a feasible allocation plan flagged `Optimization: Suboptimal (Timeout Fallback)` within **<= 12 s total elapsed time**[cite: 6]. The engine must never block beyond 12 s[cite: 6]. | Fault-injection test: inject a heavily constrained, mathematically unsolvable scenario; verify that execution terminates at the 10 s threshold and returns a valid FIFO fallback plan within 12 s across 20 trials[cite: 6]. |
| **NFR-PERF-2** | BAPLIE EDI Ingestion & Parsing Throughput | **Small Call:** <= 3 s (<= 1,000 TEU); **Medium Call:** <= 10 s (1,001–5,000 TEU); **Large Call:** <= 25 s (5,001–10,000 TEU) — measured from multipart HTTP upload completion to database transaction commit (FR-1.2.2, FR-1.2.3)[cite: 6]. | Benchmark test using synthetically generated, strictly compliant BAPLIE D.17A test files at the three stated volume tiers; 20 test runs per tier; pass criterion: >= 95% within latency targets[cite: 6]. |
| **NFR-PERF-3** | REST API Response Times | Under normal evaluation load (<= 50 authenticated concurrent sessions):<br>• Single-resource read: p95 <= 500 ms<br>• List/filtered query: p95 <= 1,200 ms<br>• Write/mutation: p95 <= 800 ms<br>• Field status update: p95 <= 500 ms[cite: 6] | Automated API benchmark suite (k6/Postman Newman) executing 500 requests per endpoint category against a pre-seeded reference database[cite: 6]. |
| **NFR-PERF-4** | Real-Time Dashboard Propagation Latency | Changes committed to the data store must reflect on connected Port Authority and Terminal dashboards within **<= 5 seconds** via Server-Sent Events (SSE), without manual browser refresh (FR-1.4.5, FR-1.6.1)[cite: 5, 6]. | Automated end-to-end timing test: trigger a database write via REST API; measure elapsed time until payload receipt on a connected headless browser client; 50 test iterations; pass criterion: p95 <= 5 s[cite: 6]. |
| **NFR-CAP-1** | Port-Agnostic Topological Scale | The Unified Port Data Model and Engine must support configurations ranging from **1 terminal / 5 berths** (minimum viable port) up to **10 terminals / 50 berths** with **zero schema modifications, zero code changes, and zero container redeployment**[cite: 6]. | Integration test: instantiate two synthetic port configurations (Port A: 2 terminals / 8 berths; Port B: 10 terminals / 50 berths) purely via the Onboarding API; verify successful recommendation generation on both[cite: 6]. |
| **NFR-CAP-2** | Concurrent Session & Pipeline Capacity | The system must sustain:<br>• >= 50 simultaneous authenticated web sessions<br>• >= 15 concurrent active Berthing Request pipelines<br>• >= 30 concurrent field actor mobile/tablet connections<br>• >= 5 parallel recommendation solver runs<br>without exceeding NFR-PERF latency ceilings or exceeding a 0.5% HTTP 5xx error rate[cite: 6]. | 30-minute continuous load test (Locust) running all concurrency dimensions simultaneously on local test infrastructure; monitor memory, CPU, and latency percentiles[cite: 6]. |
| **NFR-CAP-3** | Representative Peak Operational Data Volume | The persistent storage layer must maintain indexed query performance (meeting NFR-PERF-3) when seeded with a **Representative Peak Operational Dataset**:<br>• >= 1,000 vessel master records<br>• >= 5,000 berthing requests<br>• >= 50,000 TEU container manifest entries<br>• >= 20,000 deviation log entries<br>• >= 50,000 audit log records[cite: 6] | Database benchmark test: seed database to target volumes using synthetic fixture generation scripts; execute 1,000 complex filtered queries; verify p95 latency <= 500 ms[cite: 6]. |

## 4. Category 2 — Reliability & Fault Tolerance

> **ISO/IEC 25010 Characteristic:** Reliability — Availability, Fault Tolerance, Recoverability, Integrity[cite: 6]

| NFR ID | Requirement Name & Scope | Quantitative Metric / Technical Constraint | Verification Method |
| :--- | :--- | :--- | :--- |
| **NFR-REL-1** | Test & Evaluation Availability & Crash Recovery | The system must achieve **>= 99.0% availability during active evaluation/testing sessions**[cite: 6]. In the event of an unhandled service crash, the containerized runtime must achieve **automated crash recovery (Self-Healing Restart) within <= 60 seconds** without data corruption or manual container intervention[cite: 6]. | Chaos injection test: kill the backend application process during active API load; verify Docker container auto-restart policies restore healthy `/health` status within 60 s; 10 trials[cite: 6]. |
| **NFR-REL-2** | Runtime Stability & Resource Leak Prevention | The backend services and recommendation solver must complete a **4-hour continuous sustained load test** (simulating a full peak operating shift) with **zero unhandled exceptions, zero worker crashes, and an RSS memory growth rate of <= 5%** across the test duration[cite: 6]. | 4-hour soak test using automated traffic generation (k6); log process memory consumption (RSS) and unhandled errors; pass criterion: stable memory curve, zero process crashes[cite: 6]. |
| **NFR-REL-3** | Recovery Point & Recovery Time Objectives (RPO / RTO) | • **RTO (Recovery Time Objective):** <= 15 minutes to fully restore service from cold container start[cite: 6].<br>• **RPO (Recovery Point Objective):** <= 5 minutes of data loss window, enforced via ACID transaction commits and local automated Write-Ahead Log (WAL) archiving / database volume snapshots scheduled every 5 minutes[cite: 6]. | Disaster recovery drill: forcefully drop the database container; restore from the latest snapshot and WAL archive; calculate time-to-healthy (RTO) and measure delta of unrecoverable transactions (RPO); 3 consecutive trials[cite: 6]. |
| **NFR-REL-4** | Graceful Degradation Under External Integration Failure | • **Malformed BAPLIE:** Reject with field-level syntax diagnostics; zero partial database commits[cite: 6].<br>• **Downstream TOS/PMIS offline:** Buffer outbound recommendations in persistent Redis queue; log connectivity failure; alert human dispatcher[cite: 5, 6].<br>• **Push notification failure:** Retry <= 3 times with exponential backoff; surface in-app dashboard alert on permanent failure[cite: 6]. | Fault-injection test suite mocking each external dependency failure; verify system logs expected warnings, updates circuit-breaker state, and continues normal internal processing[cite: 6]. |
| **NFR-REL-5** | Data Integrity & ACID Compliance | All multi-entity state mutations (berth allocation confirmation, resource locks, manual overrides, deviation entries) must execute within atomic, ACID-compliant database transactions (`DB::transaction`)[cite: 6]. Partial writes are prohibited: any runtime exception within a transaction boundary must trigger an immediate, complete rollback[cite: 6]. | Integration test with forced mid-transaction failure (database connection termination injected between allocation write and log write); verify database remains in consistent pre-transaction state[cite: 6]. |
| **NFR-CONC-1** | Concurrency Conflict Resolution — Optimistic Concurrency Control (OCC) | All mutable operational entities (`BerthingRequest`, `BerthAllocation`, `TugAssignment`, `PilotTask`) must maintain a monotonic entity version token (`version` integer / `ETag`)[cite: 6]. Any mutation submitted with an obsolete version token must be rejected with **HTTP 409 Conflict within <= 200 ms**[cite: 6]. Silent overwrites are strictly prohibited[cite: 6]. | Race-condition test: issue two simultaneous conflicting update requests against the same entity version; verify exactly one transaction commits while the second receives HTTP 409 within 200 ms; 50 trials[cite: 6]. |
| **NFR-SYNC-1** | Offline Synchronization Conflict Resolution — Monotonic State Machine | Field updates from Marine Pilots and Tug Masters must advance along a **strict monotonic state machine** (e.g., `ASSIGNED` -> `STARTED` -> `COMPLETED`)[cite: 6]. Field submissions cached during offline connectivity disconnects must be validated against the server's authoritative state upon reconnection[cite: 6]. If a task was modified or aborted server-side during the disconnect window, the conflicting field update must be **rejected from mutating core state, flagged, and written to the `DeviationLog`**[cite: 6]. | Offline simulation: client transitions task to `STARTED` while offline, while server transitions task to `CANCELLED`; reconnect client; verify server state remains `CANCELLED`, conflict logged to `DeviationLog`, and client alerted[cite: 6]. |

## 5. Category 3 — Security & Multi-Tenancy

> **ISO/IEC 25010 Characteristic:** Security — Confidentiality, Integrity, Non-Repudiation, Authenticity, Accountability[cite: 6]

| NFR ID | Requirement Name & Scope | Quantitative Metric / Technical Constraint | Verification Method |
| :--- | :--- | :--- | :--- |
| **NFR-SEC-1** | Hierarchical Multi-Tenancy & Intra-Port Isolation | **Tier 1 (Port-to-Port):** Complete logical and data separation across distinct port authorities; no cross-port data access is possible[cite: 6].<br>**Tier 2 (Intra-Port Commercial Isolation):** Enforced via Row-Level Security (RLS) policies / Eloquent Global Scopes and repository token-scoping[cite: 4, 6]. Competing terminal operators (e.g., Terminal A vs. Terminal B) within the same port cannot view each other's cargo manifests, stowage plans, internal yard plans, or operational costs[cite: 6]. Any unauthorized cross-terminal query must return **HTTP 403 Forbidden**[cite: 6]. Shared marine infrastructure is visible solely through the Port Authority operational role[cite: 6]. | Security test suite: authenticate as Terminal A user; execute direct API queries targeting Terminal B vessel manifest and yard resources; pass criterion: 100% of requests return HTTP 403 with zero data leakage[cite: 6]. |
| **NFR-SEC-2** | Role-Based Access Control (RBAC) Enforcement | Enforced strictly at the API gateway and service authorization layers (via Laravel Middleware, Gates, and Policies)[cite: 5, 6]. Role tiers conform to the system actors specification: Platform Admin (SaaS Admin), Port Authority Management/Staff, Marine Department Officers/Field Workers, Terminal Planners/Supervisors (scoped to Container Terminal or Non-Container Terminal), and Marine Safety Officer (Non-Container scope)[cite: 4, 6]. Field workers (Pilots, Tug Masters) may only view tasks explicitly assigned to them[cite: 4, 6]. | Automated security matrix test: execute 30 distinct cross-role unauthorized endpoint calls; pass criterion: all unauthorized calls rejected with HTTP 403 Forbidden[cite: 6]. |
| **NFR-SEC-3** | Authentication & Token Security | Token-based authentication (JWT with RS256 asymmetric signing or equivalent via Laravel Passport / JWT package)[cite: 6]. Token expiry: Web sessions <= 15 minutes (refresh token <= 24 h); Mobile field sessions <= 60 minutes (refresh token <= 7 days)[cite: 6]. Account lockout: minimum 15-minute lock triggered after >= 5 consecutive failed authentication attempts[cite: 6]. Immediate token invalidation supported on demand[cite: 6]. | Penetration test: attempt brute-force login past threshold; verify lockout[cite: 6]. Inspect decoded JWT payload to verify RS256 signature and claim expiration boundaries[cite: 6]. |
| **NFR-SEC-4** | Cryptographic Protection in Transit | All external and inter-service HTTP communications must enforce **TLS 1.3** as the primary secure protocol[cite: 6]. TLS 1.0 and 1.1 are strictly prohibited[cite: 6]. Weak and deprecated cipher suites (e.g., RC4, 3DES, CBC-mode ciphers) must be rejected by the web server / reverse proxy (NGINX) configuration[cite: 5, 6]. | Local automated TLS audit using `testssl.sh` against the containerized reverse proxy endpoint; pass criterion: TLS 1.0/1.1 rejected, TLS 1.3 negotiated, zero insecure ciphers accepted[cite: 6]. |
| **NFR-SEC-5** | Cryptographic Protection at Rest | All persistent storage volumes containing operational data, database files, and automated backups must be encrypted using **AES-256**[cite: 6]. Cryptographic keys must be externalized from the source code repository and injected securely via deployment environment variables (`.env`)[cite: 6]. | Automated static-analysis scan checking for hardcoded secrets/keys in source control, plus verification of local storage engine AES-256 volume encryption flags[cite: 6]. |
| **NFR-SEC-6** | Append-Only Cryptographic Audit Logging | All critical operational mutations (berth override, recommendation acceptance/rejection, user login, manual schedule edits, BAPLIE upload) must append an immutable entry to the audit log (actor ID, role, timestamp, entity ID, before-state, after-state)[cite: 6]. Audit records must be write-once, append-only: database-level constraints and Eloquent model safeguards must reject any `UPDATE` or `DELETE` commands issued against the audit log table[cite: 6]. | Negative database test: attempt direct SQL `UPDATE` and `DELETE` queries against the audit log table using an administrative role; verify database engine aborts operation with permission/trigger error[cite: 6]. |
| **NFR-SEC-7** | Commercial Manifest Data Sanitization | BAPLIE manifest data (container numbers, consignee identities, hazardous classifications, stowage tiers) is classified as commercially sensitive[cite: 6]. Manifest data must be automatically filtered and stripped from any API response, logs, or dashboard views delivered to users outside the owning terminal's scope[cite: 6]. | API response schema inspection test: query common vessel call status from a Port Authority account and a competing Terminal account; verify manifest and stowage detail arrays are omitted[cite: 6]. |

## 6. Category 4 — Compatibility & Interoperability

| NFR ID | Requirement Name & Scope | Quantitative Metric / Technical Constraint | Verification Method |
| :--- | :--- | :--- | :--- |
| **NFR-INT-1** | UN/EDIFACT BAPLIE D.17A Compliance | Ingestion parser (Python Satellite) must process all mandatory and conditional segments of the UN/EDIFACT BAPLIE D.17A specification (UNA, UNB, UNH, BGM, DTM, LOC, MEA, FTX, GID, DIM, TMP, EQD, NAD, CNT, UNT, UNZ)[cite: 4, 6]. Parsing must be non-destructive: unrecognized or deprecated extension segments must generate diagnostic warnings in the parse log without aborting the ingestion of valid container slots[cite: 6]. | Test suite parsing a corpus of four distinct BAPLIE files: (1) minimal valid manifest, (2) fully populated 5,000-TEU manifest, (3) manifest with optional segments missing, (4) manifest with custom vendor segments; verify 100% extraction accuracy without process abortion[cite: 6]. |
| **NFR-INT-2** | RESTful API Conformance & RFC 9457 Errors | All exposed Laravel web services must strictly follow RESTful architectural constraints over JSON[cite: 5, 6]. All client-side and server-side errors must conform to **RFC 9457 (Problem Details for HTTP APIs)** schema[cite: 6]. All list endpoints must mandate cursor-based or offset/limit pagination to prevent memory exhaustion[cite: 6]. Complete API documented via **OpenAPI 3.0 (Swagger)**[cite: 6]. | Contract testing using `Schemathesis` or `Dredd` validating the running API against the OpenAPI 3.0 specification; automated schema check confirming RFC 9457 structure on all 4xx/5xx responses[cite: 6]. |
| **NFR-INT-3** | Multi-Format Berthing Request Adapter Interface | The ingestion subsystem must expose an abstract adapter interface capable of transforming incoming vessel berthing requests across four native channels into a unified canonical entity: (1) REST JSON payload, (2) Bulk CSV upload, (3) Excel (.xlsx) workbook, (4) Port Authority manual UI form[cite: 6]. Adapter column mappings must be configuration-driven without requiring code compilation[cite: 6]. | Integration test: submit the identical vessel call dataset across all four channels; verify that resulting database records in the canonical `BerthingRequest` table are byte-for-byte semantically identical[cite: 6]. |
| **NFR-INT-4** | Decoupled Integration with Downstream TOS & PMIS | The system must operate with complete architectural decoupling from external execution systems (e.g., Navis N4, SPS-Harbor)[cite: 4, 6]. The core recommendation engine and data pipeline must remain 100% functional when downstream integration adapters are disconnected or offline[cite: 6]. Outbound recommendations must support human-readable export format for manual entry fallback[cite: 6]. | Fault-injection test: sever downstream adapter network connections; trigger a recommendation cycle; verify engine successfully generates and persists recommendations, and formats display for manual entry fallback[cite: 6]. |
| **NFR-INT-5** | International Maritime Single Window (IMO FAL) Standard Readiness | The core data model for vessel clearances and berthing notifications must conform to the **IMO Compendium on Facilitation and Electronic Business (FAL)** data elements (e.g., IMO vessel number, voyage identifier, shipping agent reference)[cite: 6]. Integration with specific national single-window implementations (Reference: Egyptian Maritime Single Window - EMSW) must be achievable strictly via pluggable integration adapters without altering core entity schemas[cite: 4, 6]. | Architecture schema review: cross-reference the Unified Port Data Model vessel and request schemas against the IMO FAL Compendium data element directory; verify 100% representation coverage[cite: 6]. |

| **NFR-EXT-4** | Automated Unit & Integration Test Coverage | The codebase must maintain the following minimum automated test coverage thresholds in CI:<br>• Recommendation & Allocation Algorithms: >= 80% line coverage<br>• BAPLIE EDI Parsing Engine: >= 90% line coverage<br>• RBAC & Authorization Layer: >= 90% branch coverage<br>• State Tracking & Deviation Logic: >= 75% line coverage<br>• API Endpoint Handlers: >= 70% line coverage[cite: 6] | Automated test runner execution (e.g., PHPUnit, Pest, PyTest) generating coverage reports on every commit; coverage thresholds enforced as mandatory passing gates in the build pipeline[cite: 6]. |
| **NFR-EXT-5** | Dynamic Operational Configuration Externalization | All operational business rules subject to operational variance must be externalized into configuration stores, modifiable at runtime by authorized Port Authority administrators without code modification or service restart: (1) Notification lead times; (2) Deviation delta thresholds; (3) Tug allocation matrix by vessel displacement; (4) Pilot qualification rules; (5) Berth physical tolerance limits[cite: 6]. | API test: modify a business rule (e.g., change deviation logging threshold from 15 min to 30 min) via configuration endpoint; verify that the next immediate recommendation run applies the updated rule without container reboot[cite: 6]. |

| **IMO** | International Maritime Organization — United Nations specialized agency responsible for maritime safety and standardisation[cite: 6]. |

| **RBAC** | Role-Based Access Control — policy restricting system operations based on authenticated actor roles[cite: 4, 6]. |
| **RLS** | Row-Level Security — database-enforced security filtering restricting table row access dynamically based on tenant and role identifiers (NFR-SEC-1)[cite: 4, 6]. |
| **RPO** | Recovery Point Objective — maximum allowable data loss window (in minutes) following an unhandled system failure[cite: 6]. |
| **RTO** | Recovery Time Objective — maximum allowable elapsed time to restore healthy system operation following a disaster[cite: 6]. |
| **TEU** | Twenty-foot Equivalent Unit — standard international measurement unit for container cargo capacity[cite: 6]. |
| **TLS** | Transport Layer Security — cryptographic protocol securing network communication (mandated TLS 1.3 in NFR-SEC-4)[cite: 6]. |
