# F09 · Roles, abilities and scope

Task origin: P2-D1 (Sprint 2, backend PR #49), built on the profile of P1-C1 (F07). Facts checked against `develop` at `106b40e`. Paths are inside `project-backend/ATLANTECH/` unless stated. The write chain that orders these checks is F11; the audit writer is F10.

## 1. What it does

Every signed-in request is checked against **what the caller's one active role may do** and, for terminal staff, **which terminal** they may touch. Four mechanisms:

| Mechanism | Question it answers | Refusal |
| --- | --- | --- |
| **Ability** (`ability:<name>` middleware, `Gate` per ability) | May this role call this endpoint at all? | 403 `FORBIDDEN` |
| **Terminal scope** (`terminal.scope` middleware, `TerminalScope` service) | Is the terminal in this request the caller's own (for `TERMINAL_*` roles)? | 403 `FORBIDDEN` |
| **Own tasks** (`RestrictsToOwnTasks` trait on `PlanComponent`) | Is this task assigned to me (pilot, tug master, terminal supervisor)? | 403 `FORBIDDEN` |
| **No active role** | The user has no role at all | 403 `FORBIDDEN` everywhere except sign-in, `auth/me`, `auth/change-password` and `auth/logout` |

Facts:

- 12 roles (`Role`), 27 abilities (`Ability`), one fixed matrix (`RolePermissions`). **No inheritance**: a manager holds only the manager functions (lead answer Q8).
- A role the user lacks, another terminal's record, or another user's task all answer **403, never 404**, so the API does not reveal whether a record exists (lead answer Q2).
- Every refusal writes a `REJECTED_ATTEMPT` audit row with a reason (FR-GL-02); a successful call writes nothing.
- The matrix is published for Frontend and QA as `PortHub/contracts/role-matrix.md`, generated by `php artisan atlantech:contracts-role-matrix`.

It does **not**: manage users or assign roles (P2-E1/E2), check the terminal *type* (container or not; the endpoint does, see 8), check a terminal id that no middleware can see (an id in a body or query needs a manual `TerminalScope::authorize` call), or filter lists by terminal automatically (an endpoint calls `TerminalScope::restrict`). Only one endpoint carries an ability today: `GET audit-logs` (`audit.read`).

## 2. Request or data flow

### 2.1 A route with `ability:` and `terminal.scope`

1. The request reaches a route inside `port.api` (F11): `auth:web` → 401 without a session; `EnsureAccountUsable` (F08) → 403 if disabled or the password change is pending.
2. **`EnsureAbility::handle($request, $next, 'users.manage')`** (`EnsureAbility.php:30-49`):
   1. user is not an `Access\Models\User` → throw 401 `UNAUTHENTICATED`;
   2. `$role = $user->accessScope()->role` (the `AccessScope` is built once per user instance, see 3.5);
   3. role `null` → `AccessRefusal::refuse(..., NoActiveRole)` → audit + 403;
   4. `RolePermissions::allows($role, Ability::from($ability))` false → `refuse(..., RoleNotAllowed)` → audit + 403;
   5. otherwise next.
3. **`EnsureTerminalScope::handle`** (`EnsureTerminalScope.php:31-58`), only if the route has a `{terminal}` parameter:
   1. guest → 401;
   2. no `terminal` parameter → pass;
   3. the parameter is read as an id (a bound model's key, an int, or a digit string);
   4. if it is not numeric (unbound string like `abc`): a terminal-scoped user is refused (`TerminalOutOfScope`), everyone else passes;
   5. otherwise `TerminalScope::authorize($request, $user, (int) $id)`: no role → `NoActiveRole` refusal; `! $scope->canReachTerminal($id)` → `TerminalOutOfScope` refusal.
4. Later chain steps (F11), then route binding (`SubstituteBindings`) — **after** the scope checks, so an unauthorised caller never learns whether a terminal exists (a missing terminal gets the same 403: `TerminalScopeTest` "answers 403 for a terminal that does not exist").
5. The controller runs. For a body id it calls `TerminalScope::authorize` itself; for a list it calls `TerminalScope::restrict($query, 'terminal_id', $user)`; for a task it calls `$component->authorizeTask($request, $user)` or queries `PlanComponent::visibleTo($user)`.

### 2.2 A refusal (what `AccessRefusal::refuse` does)

`AccessRefusal::refuse(Request, User, AccessRefusalReason): never` (`AccessRefusal.php:23-36`):

1. `AuditService::rejectedAttempt(route, ErrorCode::Forbidden, $reason->value, $user->id, $user->username, 'users', $user->id)` — a new audit row in its own transaction (F10). `route` is `"GET /api/v1/test/ability"` style: method, a space, `/` and the path.
2. throws `ApiProblemException(ErrorCode::Forbidden)` → 403 problem JSON (F03).

The audit row: `action REJECTED_ATTEMPT`, `actor_id` and `entity_id` = the user, `entity_type 'users'`, `before_state NULL`, `after_state {route, status: 403, code: 'FORBIDDEN', reason, username}`.

### 2.3 Publishing the matrix

`php artisan atlantech:contracts-role-matrix [--output=path]` (`composer contracts:role-matrix`) writes `PortHub/contracts/role-matrix.md` from the code (3.9).

### 3.5 `AccessScope` (`app/Modules/Access/Services/AccessScope.php`)

`final readonly class` — what a signed-in user may reach.

| Member | Detail |
| --- | --- |
| Properties | `int $userId`, `?Role $role`, `list<int> $terminalIds` |
| `static for(User): self` | `loadMissing('activeRoleAssignment.organizationUnit')`; `terminalIds = [(int) terminal_id]` only when the active assignment's `unit_type` is `TERMINAL` and the unit has a `terminal_id`, else `[]`; `role` from the assignment or `null` (`AccessScope.php:25-33`) |
| `hasRole()` | `role !== null` |
| `isTerminalScoped()` | `role?->isTerminalScoped() ?? false` |

Built once per `User` instance (`User::accessScope()` caches it), so a request does one query for the relation. "Memoised" also means it can be stale if the role changes during the same instance's life.

### 3.6 `TerminalScope` (`app/Modules/Access/Services/TerminalScope.php`)

Constructor: `AccessRefusal`.

| Method | Input → behaviour |
| --- | --- |
| `authorize(Request, User, int $terminalId): void` | no role → refuse `NoActiveRole`; `! canReachTerminal` → refuse `TerminalOutOfScope`; else returns. For ids in a body or query. |
| `restrict(EloquentBuilder\|Builder $query, string $column, User): same type` | no role → `whereRaw('1 = 0')` (empty result); terminal-scoped → `whereIn($column, $terminalIds)`; otherwise unchanged. Works on Eloquent and query builders. |

### 3.7 `EnsureTerminalScope` and `EnsureAbility`

Described in 2.1. Details to know:

- `EnsureAbility` throws `\ValueError` (500) if a route names an ability that does not exist (`Ability::from`). `RouteAbilityCoverageTest` catches typos before that (3.11).
- `EnsureTerminalScope` reads only the route parameter named exactly **`terminal`**. A parameter named `{terminal_id}` or `{id}` is not seen.
- Both take their `User` from `$request->user()` and treat anything that is not `Access\Models\User` as a guest (401).

### 3.8 `AccessRefusal` and `AccessRefusalReason`

`AccessRefusal` — see 2.2; the **one** place that audits and answers a 403 for a role, terminal or own-task refusal. `AccessRefusalReason` (string enum, written into `after_state.reason`, `@not-stored`):

| Case | Value | Raised by |
| --- | --- | --- |
| `NoActiveRole` | `no_active_role` | `EnsureAbility`, `TerminalScope::authorize`, `authorizeTask` |
| `RoleNotAllowed` | `role_not_allowed` | `EnsureAbility` |
| `TerminalOutOfScope` | `terminal_out_of_scope` | `EnsureTerminalScope`, `TerminalScope::authorize`, `authorizeTask` |
| `NotOwnTask` | `not_own_task` | `authorizeTask` |

### 3.9 `RestrictsToOwnTasks` (`app/Modules/Access/Models/Concerns/RestrictsToOwnTasks.php`) and `PlanComponent`

A trait for a model with the columns `assigned_user_id` and `terminal_id`. `PlanComponent` (`app/Modules/Plan/Models/PlanComponent.php:32`, `use HasFactory, RestrictsToOwnTasks`) is the only user today; P5-O1 extends it.

| Method | Behaviour |
| --- | --- |
| `scopeVisibleTo(Builder $query, User $user): Builder` (use as `PlanComponent::query()->visibleTo($user)`) | no role → `whereRaw('1 = 0')`; not a field role → query unchanged; field role → `where(<table>.assigned_user_id, $user->id)`, and for a terminal-scoped one (the supervisor) also `whereIn(<table>.terminal_id, $terminalIds)` |
| `authorizeTask(Request, User): void` (call on a loaded row) | no role → refuse `NoActiveRole`; not a field role → return; `(int) assigned_user_id !== $user->id` → refuse `NotOwnTask`; terminal-scoped and the row's `terminal_id` not in the user's terminals → refuse `TerminalOutOfScope` |

Design points:

- It is a **local scope**, not a global scope, on purpose: AI workers, jobs and the dispatcher must still read every row (`OwnTasksTest` "is a local scope: workers and jobs still read every component").
- It lives in **Access** (a trait), and **Plan** (a later layer) uses it. Access cannot read a Plan table (layer rule, A4), so the rule could not be written the other way round. The trait takes the table's columns by name (`qualifyColumn`), so Access never names the `plan_components` table.
- Office roles are not restricted here; their access is the ability plus the terminal checks.

## 4. Why this design

| Choice | Reason | Source |
| --- | --- | --- |
| Full 12×27 matrix now, not just the mechanism | lead wanted the matrix reviewed once, up front | P2-D1 Q1 |
| 403 for a record outside the scope, not 404 | does not reveal whether a record exists | P2-D1 Q2 |
| "CT only" (container terminal) check for the terminal admin lives in the endpoint | Access cannot read `terminals` (layer rule) | P2-D1 Q3 |
| Any office role reads the general port picture; admin area is Port Admin only; field roles only own tasks | Users & Actors prose has no matrix; lead settled it | P2-D1 Q4 |
| Refusals audited through one small class | FR-GL-02; same shape as the password gate | P2-D1 Q5, N6 |
| "My tasks" is a trait now, extended in P5-O1 | the real task table is a later layer | P2-D1 Q6 |
| `MARINE_SAFETY_OFFICER` holds **no ability** | the role is for Non-Container work, which is deferred; nothing for it is built, so any ability would be invented. The role still exists in the enum and signs in (200 on `auth/me`) but is 403 elsewhere | P2-D1 Q7 (lead, 2026-11-03) |
| No inheritance between roles | a manager must not silently gain officer rights | P2-D1 Q8 |
| Publish the matrix in PortHub, generated | Frontend menus (FE-022) and QA (FE-102) read it; code stays the source of truth | P2-D1 Q9 |
| Field roles have no web abilities | decision DEC-48: pilot, tug master and terminal supervisor use the mobile app; the web shows P-20 | DEC-48 (Closed; the repo copy still said Open, fixed by backend PR #46) |
| One Gate per ability **and** a middleware | Gates serve policies and later code; the middleware adds audit and the 401/403 split | P2-D1 §3 |
| `terminal.scope` runs after `ability:` and before route binding | the check order of FR-GL-01 and no 404 for unauthorised callers (priority list in `bootstrap/app.php`, F11) | FR-GL-01 |
| Access cannot read `Plan` or `MasterData` tables | module layers: Access is layer 2, MasterData 4, Plan 8, and a module uses only earlier ones; `ModuleArchitectureTest` enforces it. So terminal checks take an id the endpoint gives them, and "own tasks" is a trait Plan imports | A4; `ModuleArchitectureTest` |

## 5. How it connects

- **Calls:** `RolePermissions`, `AccessScope`, `AccessRefusal` → `AuditService::rejectedAttempt` (F10) and `ApiProblemException`/`ErrorCode::Forbidden` (F03).
- **Called by:** every route that declares `ability:` (today `audit-logs`, F10); `UserProfileResource` (F07) reads `AccessScope`; future endpoint tasks (P2-F*, P3-*) call `TerminalScope` and `visibleTo`.
- **Position in the write chain (F11):** `auth:web` → password gate (F08) → **`ability:`** → **`terminal.scope`** → `app.version` → `license.write` → route binding → `version.token`. The order is fixed by the priority list, not by how a route lists its middleware (`WriteChainOrderTest`).
- **Depends on:** F07 (user, assignment, unit), F08 (gate first), F10, F03.
- **Layer rules:** Access uses only Shared. `PlanComponent` (Plan) uses the Access trait; Access never names Plan.
- **Other teams:** Frontend (menus from `role-matrix.md`), QA (cross-role tests), AI team indirectly (terminal isolation is requirement AIBD-024).

## 8. Gotchas and invariants

- **Every new route needs `ability:<name>` and must be inside `port.api`**, or `RouteAbilityCoverageTest` fails. Adding a name to `ABILITY_FREE_ROUTES` in that test is a security decision: say why in the PR.
- **A route with a `{terminal}` parameter must also carry `terminal.scope`** (the test enforces it). The parameter must be literally named `terminal`.
- **`terminal.scope` only sees the route.** A `terminal_id` in a JSON body or query is not checked; call `TerminalScope::authorize` in the controller. A list endpoint must call `TerminalScope::restrict`. Nothing flags a forgotten call (Open point).
- **Terminal *type* is the endpoint's job** (equipment and yard only for container terminals, Q3).
- **Order matters and is set centrally.** Never reorder `bootstrap/app.php`'s `priority` list to "fix" a route; F11.
- **Changing the matrix means changing four things:** `RolePermissions`, the expected table in `RolePermissionsTest`, the version and change log in `PublishRoleMatrix`, and then run `composer contracts:role-matrix` and open the paired PortHub PR.
- **Adding an `Ability` case without giving it to a role** fails `RolePermissionsTest` ("grants every ability to at least one role"), and the published matrix gains a row with no `yes`.
- **403 everywhere for a role-less user** except the four open routes. This is by design (lead answer N2 of P1-C1); a user whose role was ended in the database still signs in.
- **Gates and middleware are two paths to the same answer.** Change the matrix only in `RolePermissions`; never add a second source.
- **`User::accessScope()` is memoised per instance.** In tests that change an assignment after the first call, use `$user->fresh()`.
- **Never raw-query field-user data.** `visibleTo` only helps when the endpoint uses it; a worker query is intentionally unrestricted.
- **`isFieldRole` and `isTerminalScoped` are independent.** The supervisor is both: own tasks *and* own terminal.
- **`PORT_GM` is not a superuser.** It lacks every workflow ability (`berthing-requests.manage`, `plans.confirm`, ...). `plans.safety-exception` is the only plan power it holds.

## 9. How to extend it

**Add an ability and protect a new route (step by step).**

1. Add a case to `Ability` with a value in the `area.verb` style, in the right group (`'baplie.manage'`).
2. Give it to the right roles in `RolePermissions::abilitiesFor`.
3. In `RolePermissionsTest::expectedRoleMatrix()` add the row with the roles that hold it. `RolePermissionsTest` will fail until the code and the table agree (also the "27" count: update it).
4. In `routes/api.php` add the route **inside** `Route::middleware('port.api')->group(...)` with `->middleware('ability:<value>')` and a `->name('...')`. If the URL has a terminal, name the parameter `{terminal}` and add `terminal.scope`. If a version token applies, add `version.token:<param>` (F12).
5. In the controller, call `TerminalScope::authorize` for ids in the body and `TerminalScope::restrict` for lists; use `PlanComponent::visibleTo` for task lists.
6. Run `vendor/bin/pest tests/Unit/Modules/Access tests/Feature/Access tests/Feature/Api/RouteAbilityCoverageTest.php`. `CrossRoleSecurityTest` picks the new ability up automatically (it loops over `Ability::cases()`).
7. Bump `VERSION` and add a `CHANGE_LOG` line in `PublishRoleMatrix`, run `composer contracts:role-matrix`, and open the paired PortHub PR (F14). Add the route to `openapi/port-api.yaml` (F04).

**Move a role's permissions.** Edit the `match` arm in `RolePermissions` and steps 3 and 7 above.

**Give the Marine Safety Officer abilities (when the Non-Container work starts).** Add the abilities (the change log already mentions a `storage.manage` placeholder), put them in the `MarineSafetyOfficer` arm, change `RolePermissionsTest` ("gives the marine safety officer no ability"), bump the matrix version.

**Add a second terminal per user.** `AccessScope::terminalIds` is already a list, `EnsureTerminalScope` uses `in_array`; only `AccessScope::for` (one unit per assignment) and DEC-36 (one active role) would change.

**Add another own-task model.** Use `RestrictsToOwnTasks` on any model with `assigned_user_id` and `terminal_id`; if the columns differ, change the trait (P5-O1 plans that).

**Add a new refusal reason.** Add a case to `AccessRefusalReason` and call `AccessRefusal::refuse` with it; add a row to `RefusalAuditTest`.

## 11. Open points

- **Nothing forces a body/query terminal id or a list to be scoped.** `terminal.scope` only protects `{terminal}` routes; a controller can forget `authorize`/`restrict`. A review checklist item for every P2-F*/P3 endpoint.
- **Two paths to one answer:** Gates (`AccessServiceProvider`) and `EnsureAbility` both consult `RolePermissions`. Today only the middleware is used by routes.
- **`MARINE_SAFETY_OFFICER`** holds nothing until the Non-Container work (Q7); the change log mentions `storage.manage` as pending.
- **Terminal-type check** (container terminals only for equipment and yard) is left to the endpoints (P2-F4 and others).
- **`terminal.scope` parameter name** must be `terminal`; a differently named parameter would silently skip the check unless `RouteAbilityCoverageTest`'s rule is widened (it looks for `terminal` only).
- **`role-matrix.md` status is "Draft: for review by Frontend and QA"**; no team review is recorded yet (team review rule: Backend is the source of truth).
- **Own-task scope** knows only `PlanComponent`; P5-O1 extends it (more task tables, mobile).
- **Assignments with more than one active unit** are impossible by design (DEC-36); P2-E2 builds the assign/end role endpoint with the unit check.
- The `Ability` and `AccessRefusalReason` enums are `@not-stored` (outside the status vocabulary, CT-21); `PublishStatusVocabulary` leaves out any enum whose file contains `@not-stored` (`PublishStatusVocabulary.php:53`, F14), so keep that tag on both.
